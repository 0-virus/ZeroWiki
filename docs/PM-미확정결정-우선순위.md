### 2.1 결정 #1 — UD-27: 한국어 종합 시 원문 전문 용어 병기 정책

**출처:**
- `docs/ZeroWiki-요구사항-정의서.md` 12.2절 (UD-27)
- `docs/ZeroWiki-요구사항-정의서.md` 5.15절 FR-UIX-14
- 기획서 4절(초기 사용자: 논문·전문 분야 학습자)

**상황:**
- UD-24(2026-07-29) 사용자 확정: 원본 언어와 무관하게 위키 본문은 **한국어로 종합**
- 파생 의문: 영어 논문 "attention mechanism"을 위키에서 어떻게 표현하는가?

**선택지:**

**A. 전면 병기** — 한국어 정의 + 영문 원어를 항상 함께 표기
```
주의 기제(attention mechanism)는 신경망이 입력의 특정 부분에 집중하는 메커니즘이다.
```
- **장점**: 학습자가 원문·외부 자료와 대조 용이. 논문·학술 검색 시 용어 대응 명확
- **단점**: 가독성 저하. 토큰 비용 증가 (영문 10~15% 추가). 일반 사용자 혼동 가능

**B. 초기 등장 + 전문 용어만 병기** — 첫 등장 1회와 정의/중요 섹션에만 병기
```
주의 기제(attention mechanism)는 신경망이 입력의 특정 부분에 집중하는 메커니즘이다.
후속 문장에서는 "주의 기제"만 사용. 정의나 복잡한 개념에만 (영문) 병기.
```
- **장점**: 가독성·토큰 비용의 균형. 학습자도 첫 번 뜻을 이해하고 계속 진행
- **단점**: 정책 구현이 복잡 (LLM에서 "첫 등장/중요도"를 판단). 학습자가 중간에 용어 대조 필요 시 놓칠 수 있음

**C. 병기 없음** — 한국어 정의만 제공, 영문 병기 전혀 안 함
```
주의 기제는 신경망이 입력의 특정 부분에 집중하는 메커니즘이다.
```
- **장점**: 가독성 최고. 토큰 비용 최소. 일반 사용자 친화적
- **단점**: 논문 학습자가 원문과 대조 불가. 기획서 4절 "초기 사용자 포함" 가치 하락

**팀 권고 (미확정):** **B. 초기 등장 + 중요 개념 병기**
- **근거**: 기획서 4절 "초기 사용자에 논문 학습자 포함"과 "일반 사용자" 양쪽 밸런스
- **구현**: Ingest 프롬프트에 "처음 등장 + 정의 섹션 + 복잡한 주장은 영문 병기"로 지시

**되돌리기 비용:**
- A→B 또는 A→C: 기존 Ingest한 위키 페이지의 프롬프트 규칙 변경 시 재처리 필요 (높음)
- B→C: 약간의 가독성 개선 (낮음)
- C→B: 기존 페이지 재처리 필요 (중간)

**차단 단계:** Ingest 프롬프트 작성 **반드시 확정 필요** (Phase 1 구현 전)

### 2.2 결정 #2 — FR-NTF-05: 처리량 부족 시 사용자 알림

**출처:**
- `docs/ZeroWiki-요구사항-정의서.md` 5.12절 FR-NTF-05
- 기획서 17절 (알림 목록)
- 기획서 20절 (처리량 보류 정책)

**상황:**
- 기획서 17절: "MVP는 서비스 내부 알림만 지원한다" + 5개 목록 (위험 변경 / Lint 결과 / 포크 업데이트 / 편집 제안 / 계정 삭제 유예)
- 기획서 17절 마지막: "단순 Import 완료는 활동 영역에 표시하되 별도 중요 알림으로 강제하지 않는다"
- 이 구조는 목록이 **완전하고 닫혀 있음**을 시사
- 그런데 기획서 20절: "처리량 부족 시 작업 보류 후 추가 처리량 구매"를 요구
- 사용자가 처리량 부족을 모르면 대응 불가능 → 알림 필요

**판정:** 기획서 17절의 알림 목록이 닫힌 집합이므로, 새로운 알림 타입은 **사용자 결정**

**선택지:**

**A. 기획서 17절 알림 목록에 추가** — "처리량 부족으로 작업이 보류되면 사용자에게 알린다"
- **장점**: FR-ING-22(처리량 부족 시 보류)가 실질적으로 동작. 사용자가 구매 기회를 인지
- **단점**: 알림 목록 확장. 초기 MVP는 내부 알림 5종으로 계획됨

**B. 알림하지 않고 별도 API/UI로 대응** — 작업 상세 조회 시에만 보류 상태 노출
- **장점**: 알림 목록 유지. 구독 모델 아님
- **단점**: 사용자가 처리량 부족을 모를 수 있음. 구매 기회 상실

**팀 권고 (미확정):** **A. 알림 추가**
- **근거**: 기획서 20절의 "처리량 부족 시 보류"가 의미를 가지려면 사용자에게 알려야 함

**되돌리기 비용:**
- A 선택 후 제거: 기존 알림 시스템을 다시 설계해야 함 (중간)

**차단 단계:** Phase 2 (알림 시스템 구현)

### 2.3 결정 #3 — FR-ING-26: 운영 상태 2종 (취소됨 / 처리량 보류)

**출처:**
- `docs/ZeroWiki-요구사항-정의서.md` 5.5.3절 FR-ING-26
- 기획서 20절 (비동기 처리)
- `docs/ZeroWiki-API-명세-초안.md` 6.1절

**판정:** **A. 기획서 20절에 반영** (명확화)

**근거:**

#### (1) `취소됨` 상태

- **API 명세 6.1절에 이미 `/cancel` 엔드포인트 존재:** `POST /libraries/{libraryId}/ingest-jobs/{jobId}/cancel`
- **취소 기능이 계약에 존재하면 취소 결과의 상태 표현은 필수**
- 이것은 "취소 기능을 추가할 것인가"가 아니라 **"이미 있는 기능의 상태 표현 방식"**
- 따라서 **제품 결정이 아니라 명확화** (헌법 제2조 6항)

#### (2) `처리량 보류` 상태

- **기획서 20절 같은 절에 명시:**
  - 문장 1: "작업 상태: 대기, 스캔, 계획 승인 대기, 처리, 질문 대기, 변경 승인 대기, 완료, 실패"
  - 문장 3: "처리량 부족 시 작업 **보류** 후 추가 처리량 구매"
- **동일 절 안의 내부 불일치:** 보류를 명시했는데 상태 목록에 없음
- **FR-ING-22도 "보류"를 명시:** 개념으로는 이미 확정
- **구현 방식(큐, 플래그)은 backend 기술결정이지만 상태 표현은 요구사항 층위**
- 따라서 불일치 해소는 **명확화** (헌법 제2조 6항)

**결론:** 
- 새 기능 추가가 아니라 **기획서의 누락·불일치 해소**
- 헌법 제2조 6항의 "이미 확정된 사실의 명확화"에 해당
- 기획서 수정 완료 (2026-07-29)
