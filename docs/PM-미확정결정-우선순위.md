### 2.2 결정 #1 — UD-03: Free·Basic·Advanced 처리량 단위

**출처:**
- `docs/ZeroWiki-요구사항-정의서.md` 12.1절 684행 UD-03
- `docs/ZeroWiki-API-명세-초안.md` 18절 3번
- 기획서 21절 과금 모델 (550~570행)

**상황:**
- 기획서 21절: "Free(월 10 문서) / Basic(월 50 문서) / Advanced(무제한)" 요금제 정의
- 그런데 "문서"가 처리량의 정확한 단위인가?
- 기획서 10절 Ingest 설명에서는 "문서 단위" "배치 단위"를 모두 언급
- API 명세 18절 3번에서 "처리량 단위"를 미확정으로 남겼음

**선택지:**

**A. 문서(Document)** — 수집한 파일 1개 = 1문서 (권고)
- **장점**: 사용자 이해 용이. 기획서 21절과 일치
- **단점**: 1문서가 1000개 페이지를 생성할 수 있어 처리량 예측 어려움

**B. 페이지(Page)** — AI가 생성한 페이지 1개 = 1처리량
- **장점**: 실제 처리 비용과 1:1 대응. 정확한 계량
- **단점**: 사용자가 "100 페이지 한도"의 의미를 파악 어려움. 기획서 변경 필요

**C. 토큰** — LLM 토큰 기준 (예: 10만 토큰 = 1처리량)
- **장점**: 실제 LLM 비용 반영
- **단점**: 기술 상세가 노출됨. 사용자 이해 최악

**팀 권고(미확정):** **A. 문서(Document)**
- **근거**: 기획서 21절과 일치, 사용자 이해 우선
- **보완**: 기획서 21절에 "1문서당 평균 페이지 수(예: 5~10개)"를 추정치로 덧붙여 기대값 안내

**차단 단계:** Phase 1 구현 전 **필수** (요금제 구현)

### 2.3 결정 #2 — UD-10: Notion OAuth·결제 공급자 선정

**출처:**
- `docs/ZeroWiki-요구사항-정의서.md` 12.1절 693행 UD-10
- `docs/ZeroWiki-API-명세-초안.md` 18절 10번
- 기획서 9절 입력 경로 (240~270행)
- 기획서 21절 과금 모델 (550~570행)

**상황:**
- 기획서 9절: Notion 연동을 선택지 중 하나로 제시
- 기획서 21절: "초기 프리 팀 요금제로 최소화" 방침 명시
- 하지만 OAuth 공급자(Notion SDK 버전 선택), 결제 공급자(Stripe·NHN Payco·토스페이 중 선택) 미정

**선택지:**

**Notion OAuth:**
- **A. Notion 공식 SDK (권고)** — 장기 지원, 공식 문서. 단점: 초기 심사 시간(1~2주)
- **B. 개발자 토큰** — 빠른 시작. 단점: 개인용, 프로덕션 미지원

**결제 공급자:**
- **A. Stripe (권고)** — 국제 표준, 한국 지원, 문서 풍부
- **B. 토스페이** — 국내 사용자 UX, 낮은 수수료(1.2~1.5%). 단점: 해외 사용자 미지원
- **C. NHN Payco** — 레거시, 국내만 지원

**팀 권고(미확정):**
- Notion: **A. 공식 SDK**
- 결제: **A. Stripe** (초기 MVP는 한국 사용자 중심이지만 해외 확장성 고려)

**되돌리기 비용:**
- 공급자 변경: 매우 높음 (결제 시스템 재통합, 기존 결제 기록 처리)

**차단 단계:** Phase 1 구현 전 **필수** (API 계약 확정)

기획서 21절에서 "월별 처리량 한도"를 명시했으나, 사용자에게 어떻게 표시할지 미정

#### UD-20: 감사 로그 보존 기간과 관리자 접근 정책

**기획서 배경 (18절 466~468행):**
- 계정 삭제 후 30일간 복구 가능 상태로 보관
- 30일 경과 후 원본·위키·버전·임베딩·**작업 로그**를 완전 삭제

**상황:**
기획서 18절은 **계정 삭제 시** 작업 로그를 30일 후 삭제하도록 명시했으나, **감사 로그(사용자/관리자 계정 접근 기록)**의 보존 정책은 별도로 정하지 않음. 작업 로그와 감사 로그는 다른 대상이므로 독립적 결정 필요.

**선택지:**

**보존 기간:**
- **A. 90일** — 국내 통신사 기준(3개월). 분쟁·의심 거래 조사에 충분한 시간. 저장 비용 중간
- **B. 1년** — 국제 규범(GDPR 보조 기록). 국내 개인정보보호법 권고 기간. 저장 비용 높음. **(qa 권고)**

**접근 정책:**
- **A. 관리자(제품 오너)만 조회** — 보안 우선. 초기 MVP 운영 단순화
- **B. 사용자도 자신의 로그 조회 가능** — 투명성 우선. 데이터 주체 권리 이행 필요, UI 추가 개발

**팀과 qa의 권고:**
- pm: **보존 90일 + 관리자만** (중간 선택)
- qa: **보존 1년 + 관리자만** (`docs/검증-QA-계약-확정-체크리스트.md` 2.1절)

### 2.5 결정 #4 — UD-22: 신고 처리 주체와 검토 기한

**출처:**
- `docs/ZeroWiki-요구사항-정의서.md` 12.2절 714행 UD-22
- 기획서 15절 공개·포크·편집 제안 (370~420행)
- 기획서 18절 보안 (457~470행)

**상황:**
- 기획서 15절: "개인정보·저작권·유해 콘텐츠 신고 시 검토 절차 수행"
- 기획서 18절: 삭제 정책만 명시, 신고 처리는 비어 있음
- 1인 개발 조직에 검토 주체가 없음 → **대응 정책 선택 필요**

**선택지:**

**A. 자동 임시 비공개 + 소유자 이의 제기 (권고)**
- 신고 접수 즉시: 해당 콘텐츠 임시 비공개
- 제목: "신고 대상 검토 중" 상태로 표시
- 소유자는 사유 제출 및 이의 가능
- 제품 오너가 최종 판단 (검토 기한 30일)
- **장점**: 빠른 대응, 사용자 피해 최소화
- **단점**: 오신고 시 소유자에게 피해 가능

**B. 소유자 검토 + 선택적 비공개**
- 신고 접수 후 소유자에게 알림
- 소유자가 콘텐츠 유지/삭제 선택
- 제품 오너는 분쟁 경우만 중재
- **장점**: 소유자 자율성 우선
- **단점**: 유해 콘텐츠가 계속 노출될 수 있음

**C. 제품 오너 직접 검토**
- 신고 접수 후 제품 오너가 즉시 판단
- 필요시 소유자·신고자 양쪽 의견 수집
- **장점**: 책임 명확
- **단점**: 1인 운영으로 병목. 검토 기한 장기화

**팀 권고(미확정):** **A. 자동 임시 비공개 + 이의 제기**
- **근거**: 기획서 15절의 "검토 절차" 요구 + 1인 조직의 운영 현실 균형
- **기한**: 신고 접수 30일 이내 최종 판단

**차단 단계:** Phase 3 (공개·포크, 일정 미정)
