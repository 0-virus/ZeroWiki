# ZeroWiki MVP 서비스 기획서

작성일: 2026-07-26  
상태: 사용자 인터뷰 4회 반영본

## 1. 제품 정의

### 한 문장 정의

**ZeroWiki는 사용자가 수집한 자료를 목적에 맞는 지식 구조로 지속적으로 컴파일하고, 연결·모순·출처를 관리하며, AI 사서를 통해 필요한 지식을 빠르게 꺼내 쓰는 개인 지식 도서관이다.**

### 핵심 비유

- 사용자의 자료는 장서다.
- 도서관은 특정 목적에 맞게 구성된 지식 공간이다.
- AI는 자료를 분류하고 연결하고 관리하는 사서다.
- 위키는 자료를 읽을 때마다 갱신되는 살아 있는 지식 지도다.

학습, 개인 의사결정, 실무 레퍼런스 등 사용 목적은 달라질 수 있지만, “나의 지식을 컨텍스트화한 도서관”이라는 제품의 중심은 유지된다.

## 2. 해결하려는 문제

사람들은 많은 자료를 저장하지만 다음 문제 때문에 다시 활용하지 못한다.

1. 정리한 자료를 다시 찾는 비용이 새로 검색하는 비용보다 크다.
2. 서로 다른 자료 사이의 관계를 직접 만들어야 한다.
3. 새로운 자료가 기존 지식과 충돌해도 이를 발견하기 어렵다.
4. RAG는 질문할 때마다 관련 조각을 다시 찾지만, 이전 종합과 연결이 지식 자산으로 축적되지 않는다.

ZeroWiki는 원본을 단순 검색 대상으로 보관하지 않는다. 자료를 받아 기존 위키에 통합하고, 연결과 모순을 미리 정리해 둔다.

## 3. 핵심 가치와 성공 가설

### 사용자가 얻어야 하는 결과

1. 자신의 자료에서 원하는 답을 빠르게 얻는다.
2. 직접 발견하기 어려운 자료 간 연결 관계를 발견한다.
3. 서로 다른 자료의 모순을 AI가 먼저 찾아준다.
4. 자료가 늘수록 도서관의 구조와 종합이 함께 성장한다.

### MVP 핵심 가설

> 사용자는 문서 100개를 넣은 뒤, AI가 자동으로 만든 연결과 모순이 기존 검색 또는 일반적인 RAG보다 가치 있다고 느낀다.

### 검증 기준

- 문서 100개 Import 완료율 95% 이상
- 수동 분류 없이 핵심 주제 구조 생성
- 사용자 평가에서 제안 연결의 70% 이상이 유용함
- 주요 답변에서 근거 페이지와 원본 위치 추적 가능
- 의도적으로 포함한 모순의 80% 이상 탐지
- 테스트 사용자 절반 이상이 2주 후 재사용
- 사용자 다수가 기존 검색보다 유용하다고 평가

## 4. 초기 사용자

### 핵심 사용자

특정 분야를 장기간 깊게 탐구하며 이미 50~200개 이상의 자료를 보유한 개인.

예:

- 개발·기술 학습자
- 논문과 전문 자료를 축적하는 학습자·연구자
- 건강·운동 자료를 공부해 개인 의사결정에 활용하려는 사람
- 개인 계정에서 비공개 업무 레퍼런스를 관리하려는 사람

### 초기 검증 그룹

5~10명을 목표로 한다.

- 개발·기술 학습 2~3명
- 논문·전문 분야 학습 2명
- 개인 의사결정·생활 연구 1~2명
- 비공개 업무 레퍼런스 1~2명

참가자가 실제 보유한 자료 50~200개로 테스트한다. 샘플 자료만으로는 개인 맥락에 따른 연결 가치를 검증하기 어렵다.

## 5. 제품 원칙

1. **원본 불변:** 수집한 원본은 덮어쓰지 않는다. 변경된 웹 자료를 다시 수집하면 새 버전으로 저장한다.
2. **AI 작성 우선:** 위키의 의미 있는 작성과 재구성은 AI가 담당한다.
3. **사용자 통제:** 사용자는 변경을 승인·거절·보류하고 AI의 판단을 수정할 수 있다.
4. **근거 추적:** 중요한 주장과 종합은 원본 근거로 추적할 수 있다.
5. **상태 구분:** 검증된 사실, 출처의 주장, AI 추론, 사용자 판단, 가설을 구분한다.
6. **연결 중심:** 문서 수보다 지식 간 관계와 흐름을 우선한다.
7. **목적 적응:** 동일한 원본도 도서관 목적에 따라 다르게 컴파일한다.
8. **소유권 보장:** 사용자는 원본·위키·관계·버전 정보를 범용 형식으로 내보낼 수 있다.
9. **안전한 기본값:** 도서관은 비공개가 기본이고, 도서관 간 참조도 명시적으로 허용해야 한다.
10. **점진적 개인화:** 짧은 온보딩으로 시작하고 자료와 피드백이 쌓일수록 운영 헌법을 정교화한다.

## 6. 핵심 도메인 모델

### 6.1 사용자와 공통 원본 보관소

사용자 계정에는 하나의 공통 원본 보관소가 있다.

- 하나의 원본을 여러 도서관이 참조할 수 있다.
- 동일 원본을 여러 번 물리적으로 복제하지 않는다.
- 사용자 계정 내부에서 콘텐츠 해시로 중복 후보를 찾는다.
- 사용자 간 원본 중복 제거는 개인정보 보호를 위해 하지 않는다.

### 6.2 도서관

사용자는 여러 도서관을 만들 수 있다.

- 도서관마다 목적과 운영 헌법이 있다.
- 명시적으로 연결한 도서관만 서로 참조한다.
- 참조는 단방향이다.
- 질문은 현재 도서관을 우선 검색한다.
- 근거가 부족하면 AI가 연결된 도서관으로 검색 범위를 확장할지 제안한다.

### 6.3 도서관 운영 헌법

도서관마다 자연어와 구조화 설정으로 된 운영 헌법을 둔다.

- 목적과 주요 질문
- 예상 사용자 또는 독자
- 설명 수준과 답변 깊이
- 지식 분류와 페이지 유형
- 출처 우선순위와 신뢰도 기준
- 지식 노후화 판단 기준
- 자동 연결 범위
- 위험 변경 판정 기준
- 민감정보 처리 정책
- 사용자가 거절한 연결과 그 이유

사용자는 요약된 헌법을 볼 수 있고 고급 설정에서 수정할 수 있다.

### 6.4 지식 객체

도서관마다 AI가 필요한 유형을 선택·확장한다. 초기 기본 유형은 다음과 같다.

- `Source`: 원본과 소스 요약
- `Concept`: 개념, 인물, 기술, 대상
- `Flow`: 과정, 절차, 인과관계
- `Synthesis`: 여러 자료를 종합한 분석
- `Decision`: 사용자의 판단과 근거
- `Question`: 아직 해결되지 않은 질문과 지식 공백

사용자에게는 읽기 좋은 Markdown 문서로 보이지만 내부적으로는 다음 단위를 관리한다.

- Page
- Claim
- Evidence
- Source
- Relation
- Contradiction
- Version

모순 탐지와 근거 추적은 페이지 전체가 아니라 주요 주장 단위로 수행한다.

### 6.5 지식 상태

각 주요 주장은 다음 중 하나의 성격을 갖는다.

- 검증된 사실
- 특정 출처의 주장
- AI의 종합 또는 추론
- 사용자의 판단
- 검증되지 않은 가설

AI가 출처 신뢰도를 제안하고 사용자가 이를 수정할 수 있다. 모순이 발생하면 AI는 선택지를 제시하지만 최종 채택은 사용자 판단으로 결정한다.

## 7. 도서관 템플릿

### 7.1 학습·연구

- 개념과 정의
- 원리와 인과관계
- 연구·주장 비교
- 출처 신뢰도
- 지식 공백
- 후속 탐구 질문
- 분야별 노후화 기준

### 7.2 개인 의사결정

- 목표
- 선택지
- 근거와 반대 근거
- 개인 경험
- 가설
- 결정과 결과
- 판단을 바꿀 조건

건강·운동은 별도 의료 템플릿으로 제공하지 않고 학습·연구 또는 개인 의사결정의 사용 사례로 둔다. 의료 진단이나 고위험 전문 판단은 MVP 범위에서 제외한다.

## 8. 온보딩

### 필수 질문 5개

1. 이 도서관으로 무엇을 알고 결정하거나 만들어내고 싶은가?
2. 어떤 종류의 자료를 넣을 예정인가?
3. 현재 해당 분야에 대해 어느 정도 알고 있는가?
4. 어떤 출처와 관점을 더 신뢰하는가?
5. AI가 반드시 물어봐야 하거나 조심해야 할 영역은 무엇인가?

답변과 선택한 템플릿으로 초기 운영 헌법을 만든다. 이후 Ingest 과정의 질문, 연결 거절 사유, 신뢰도 수정, Lint 결과를 반영해 헌법을 점진적으로 보강한다.

## 9. 입력 경로

### MVP 지원

1. Obsidian 저장소 Import
2. 직접 작성과 파일 업로드
3. Notion 일회성 Import
4. URL 붙여넣기 기반 웹 클리핑

### 웹 클리핑 초기 지원

- 일반 웹 아티클
- YouTube
- arXiv 및 공개 논문 페이지
- GitHub 저장소와 README
- 주요 블로그 플랫폼

공개 URL만 서버에서 가져온다. 로그인 또는 유료 콘텐츠는 사용자가 직접 파일이나 Markdown으로 제공해야 한다.

이미지는 외부 URL만 보관한다. YouTube에서 사용 가능한 자막을 얻지 못하면 처리 불가로 표시한다. 웹 원본은 자동 감시하지 않으며 사용자가 같은 URL을 다시 클리핑하면 새 버전을 만든다.

### 웹 클리핑과 크롤링의 경계

MVP는 사용자가 지정한 URL 한 건을 수집하는 클리핑을 지원한다. 사이트 링크를 자율적으로 따라가는 광범위한 크롤링은 제외한다.

## 10. Ingest 파이프라인

### 대량 Import

1. 전체 파일을 저비용 방식으로 빠르게 스캔한다.
2. 중복, 민감정보, 파일 형식, 중요도, 주제 묶음, 예상 처리량을 분석한다.
3. 처리 계획과 비용을 사용자에게 제시한다.
4. 계획 승인 후 문서별 처리를 시작한다.
5. 맥락이 불분명한 문서만 보류하고 나머지는 계속 처리한다.
6. 변경 세트를 초안 도서관에 적용해 사용자가 미리 추적할 수 있게 한다.
7. 일반 변경은 일괄 승인하고 위험 변경만 개별 승인한다.
8. 새 버전을 발행한다.
9. 대량 Ingest 완료 후 전체 Lint를 실행한다.

### 2단계 AI 처리

#### 1단계: 저비용 처리

- 파일 파싱
- 중복 후보 탐색
- 민감정보·비밀 탐지
- 주제 분류
- 기존 페이지 후보 탐색
- 처리 계획과 구조 초안

#### 2단계: 고품질 처리

- 핵심 주장과 근거 추출
- 기존 지식과 의미 있는 연결
- 종합 페이지 작성
- 모순 후보 판단
- 위험 변경 생성
- 후속 질문과 지식 공백 제안

모델명은 사용자에게 노출하지 않고 `빠른 처리`, `표준 처리`, `정밀 처리`처럼 제품 모드로 표현한다.

## 11. 변경 승인과 버전 관리

### 일괄 승인 대상

- 새 페이지
- 새 연결
- 요약 추가
- 오탈자와 어투 개선
- 기존 의미를 바꾸지 않는 구조 개선

### 개별 승인 대상

- 기존 사실 수정
- 기존 내용 삭제
- 모순 판정과 해소
- 출처 신뢰도의 큰 변경
- 페이지 병합·분할
- 대규모 구조 변경
- 포크 원본의 변경 반영

### 변경 검토 화면

GitHub Pull Request와 유사한 형태를 사용한다.

- 변경 이유
- 영향을 받는 페이지
- 변경 전후 diff
- 근거 출처
- AI 신뢰도
- 승인
- 거절
- 수정 요청
- 판단 보류

사용자가 직접 의미 있는 본문 편집을 시도하면 AI 편집과 Lint를 권장한다. 그래도 수정할 수 있으며, 수정 후 자동 Lint 대상으로 등록한다.

## 12. AI 사서와 검색

### 기본 답변

- 빠른 답변을 기본으로 한다.
- 질문에 따라 비교, 학습, 의사결정, 보고서 등 필요한 형식으로 자동 조정한다.
- 기본 화면에서는 상세 출처를 숨긴다.
- 사용자가 `근거 보기`를 선택하면 위키 페이지, 원본 위치, 출처 신뢰도, AI 종합 근거를 보여준다.

### 근거가 부족한 경우

1. 모른다고 명시한다.
2. 답변에 필요한 자료를 제안한다.
3. 연결된 도서관 확장 검색을 제안한다.
4. 웹에서 보완 자료를 찾을 수 있다면 사용자에게 웹 검색 승인을 요청한다.

### 검색 인터페이스

- 전통 검색: 페이지, 주제, 원본을 빠르게 찾는다.
- AI 사서: 여러 페이지와 주장을 종합해 답한다.

전통 검색은 탐색기 상단의 보조 기능으로 두고 AI 사서를 중심 경험으로 삼는다.

### 답변 환류

재사용 가치가 있는 답변은 자동 저장하지 않는다. 저장 전 다음을 우선 보여준다.

- 기존 페이지와의 연결
- 근거와 출처
- 새 페이지 또는 수정 위치
- 영향을 받는 페이지

사용자 승인 후 위키에 반영한다.

## 13. Lint

### 실행 시점

- 대량 Ingest 완료 후 전체 Lint
- 월간 정기 Lint
- 공개 페이지 발행 전 안전 검사
- 직접 본문을 크게 수정한 후 검사

### 검사 항목

- 깨진 연결
- 고아 페이지
- 중복 개념
- 상호 참조 누락
- 출처 없는 주요 주장
- 출처 간 모순
- 최신 자료에 의해 낡은 주장
- 낮은 신뢰도의 핵심 주장
- 도서관 목적과 무관한 연결
- 운영 헌법과 실제 구조의 불일치
- 포크 원본의 새 버전과 반영 필요성
- 지식 흐름상 중요한 공백

중요한 공백을 발견하면 보완 자료와 웹 검색을 제안한다. 사용자 승인 후에만 웹 검색과 Ingest를 수행한다.

## 14. 사용자 피드백 학습

잘못된 연결에 대해 이유를 받는다.

- 주제가 다름
- 인과관계가 아님
- 출처가 약함
- 도서관 목적과 무관함
- 중복 개념
- 기타

피드백은 기본적으로 현재 도서관의 운영 헌법과 이후 AI 판단에만 반영한다. 사용자가 선택하면 모든 도서관에 공통 선호로 적용할 수 있다.

## 20. 권장 기술 아키텍처

### 방향

1인 개발과 초기 소수 사용자에 맞춰 **Spring Boot 모듈러 모놀리스 + 별도 Worker**로 시작한다. 마이크로서비스와 전용 벡터 DB는 사용하지 않는다.

### 프론트엔드

- Next.js
- TypeScript
- 반응형 웹
- Markdown 렌더러
- diff 뷰어
- 그래프 시각화 라이브러리

### 백엔드

- Java 21+
- Spring Boot
- Spring Security
- Spring Data JPA
- PostgreSQL
- Flyway
- 구조화된 LLM 출력 검증

### 데이터

- PostgreSQL: 사용자, 도서관, 페이지, 관계, 주장, 근거, 버전, 작업, 알림, 과금 사용량
- PostgreSQL 전문 검색: MVP 키워드 검색
- `pgvector`: 의미 검색 보조
- S3 호환 객체 스토리지: 원본 파일과 Import 아카이브

### 비동기 처리

- PostgreSQL 기반 작업 큐로 시작
- API 서버와 Worker를 별도 프로세스로 실행
- 작업 상태:
  - **정상 흐름 8종**: 대기 → 스캔 → 계획 승인 대기 → 처리 → 질문 대기 → 변경 승인 대기 → 완료 또는 실패
  - **운영 상태 2종** (어느 단계에서든 진입 가능): 취소됨(사용자가 작업 취소), 처리량 보류(처리량 부족으로 중단, 추가 구매 후 재개)
- 문서별 실패 격리와 재시도
- 처리량 부족 시 작업을 보류 상태로 두고 추가 처리량 구매를 안내한다

Redis, Kafka, Kubernetes는 MVP에서 사용하지 않는다.

### LLM 계층

- 모델 공급자 어댑터
- 작업별 모델 라우팅
- 저비용 스캔 모델과 고품질 종합 모델 분리
- 토큰 사용량 기록
- 구조화 출력 스키마 검증
- 출처 없는 주장 생성 방지 검사
- 사용자 문서를 명령으로 실행하지 않는 격리 프롬프트

### 클라우드

- 애플리케이션: Railway 또는 관리 가능한 단일 VPS
- PostgreSQL: Neon 등 관리형 PostgreSQL
- 원본 저장: Cloudflare R2 등 S3 호환 스토리지

초기 월 10만 원 예산에서는 인프라 고정비를 약 3만~7만 원 범위로 유지하고 나머지를 LLM 처리에 배정한다. 실제 요금제는 문서 100개 벤치마크로 평균 처리 비용을 측정한 뒤 확정한다.

## 24. 가장 큰 제품 리스크

1. **연결 품질:** 관련 있다는 이유만으로 과도한 연결을 만들면 도서관이 소음으로 변한다.
2. **모순 오탐:** 관점 차이, 시간 변화, 적용 조건 차이를 모순으로 잘못 판정할 수 있다.
3. **AI 비용:** 대량 Ingest가 사용자 기대보다 훨씬 비쌀 수 있다.
4. **승인 피로:** 변경 승인이 많으면 자동화의 가치가 사라진다.
5. **범용 스키마:** 분야별 구조를 AI가 안정적으로 생성하지 못할 수 있다.
6. **공개 저작권:** 원본을 과도하게 재현한 페이지가 공개될 수 있다.
7. **보안:** 회사 문서와 개인 자료가 섞이면 도서관 간 정보 노출이 치명적이다.
8. **과도한 MVP:** Import, AI 컴파일, 버전, 공개, 포크를 동시에 구현하면 1인 개발 범위를 넘길 수 있다.

첫 검증에서는 공개·포크보다 개인 도서관의 Ingest 품질을 우선한다. 기능은 MVP 목록에 포함하되 개발 순서는 개인 코어 검증 뒤로 둔다.
