## 0. 이 문서의 지위와 사용법

### 0.1 목적

기획서의 서술형 제품 정의를 **검증 가능한 요구사항 단위**로 변환한다. 각 요구사항은 고유 ID, 우선순위, 대상 Phase, 기획서 출처, 검증 방법을 갖는다. ERD와 API 명세는 이 문서를 근거로 정합성을 맞춘다.

### 0.2 문서 서열에서의 위치

헌법 제2조 1항의 서열은 그대로다. 이 문서는 **기획서(1순위)의 파생 문서**이며 기술 계약(ERD·API 명세, 2순위)의 상위 근거다.

```
1순위  docs/ZeroWiki-MVP-서비스-기획서.md          제품 정의·범위·원칙
  └─   docs/ZeroWiki-요구사항-정의서.md            ← 이 문서. 기획서의 요구사항 변환
2순위  docs/ZeroWiki-ERD-초안.md
       docs/ZeroWiki-API-명세-초안.md              기술 계약
3순위  docs/검증-*.md
4순위  코드
```

이 문서가 기획서와 충돌하면 **기획서가 진실**이며, 충돌은 이 문서의 결함으로 간주해 수정한다. 이 문서가 ERD·API 명세와 충돌하면 이 문서를 근거로 두 문서를 조정한다.

### 0.3 이 문서가 하지 않는 것

- **미확정 사항을 확정하지 않는다.** 수치·정책·선택이 필요한 항목은 값을 쓰지 않고 `UD-NN`으로 참조한다(헌법 제3조). 이 문서에 숫자가 없는 자리는 "아직 정해지지 않았다"는 뜻이며, 채워 넣은 것처럼 보이게 하지 않는다.
- **설계하지 않는다.** 테이블·엔드포인트·컴포넌트를 정의하지 않는다. 그것은 ERD·API 명세·프론트엔드 설계의 몫이다.
- **기획서에 없는 기능을 추가하지 않는다.** 도출 과정에서 필연적으로 필요해진 요구사항은 `[파생]`으로 표시하고 도출 근거를 밝힌다.

### 0.4 표기 규약

| 표기 | 의미 |
| --- | --- |
| **M** | Must — MVP 성립에 필수. 빠지면 제품이 성립하지 않는다 |
| **S** | Should — MVP 포함. 미충족 시 가치가 크게 훼손되나 출시는 가능 |
| **C** | Could — MVP 포함이나 마지막에 조정 가능 |
| **X** | MVP 제외 (기획서 22절). 참조용으로만 기재 |
| `[파생]` | 기획서에 명시되지 않았으나 도출상 필요해 추가한 요구사항 |
| `UD-NN` | 미확정 사항. 12절 참조. 이 값에 의존하는 구현은 가정을 명시해야 한다 |
| 출처 | `기획서 N절` 형식. 근거 없는 요구사항은 두지 않는다 |

우선순위는 **Phase와 독립**이다. Phase는 구현 순서(기획서 23절), 우선순위는 중요도다.

## 1. 제품 목표와 성공 조건

### 1.1 제품 정의 (기획서 1절)

ZeroWiki는 사용자가 수집한 자료를 목적에 맞는 지식 구조로 지속적으로 컴파일하고, 연결·모순·출처를 관리하며, AI 사서를 통해 필요한 지식을 빠르게 꺼내 쓰는 **개인 지식 도서관**이다.

### 1.2 해결 대상 문제 (기획서 2절)

| ID | 문제 | 대응 요구사항군 |
| --- | --- | --- |
| P-1 | 정리한 자료를 다시 찾는 비용이 새로 검색하는 비용보다 크다 | FR-ASK, FR-SCH |
| P-2 | 자료 간 관계를 사용자가 직접 만들어야 한다 | FR-KNW (관계 자동 생성) |
| P-3 | 새 자료가 기존 지식과 충돌해도 발견하기 어렵다 | FR-KNW (모순 탐지), FR-LNT |
| P-4 | RAG는 매번 조각을 찾을 뿐 종합이 자산으로 축적되지 않는다 | FR-ING, FR-KNW, FR-CHG |

**P-4가 제품의 차별점이다.** 어떤 요구사항이 P-4를 훼손한다면(예: 종합 결과를 저장하지 않고 매번 재생성) 그 요구사항은 잘못된 것이다.

### 1.3 MVP 성공 가설 (기획서 3절)

> 사용자는 문서 100개를 넣은 뒤, AI가 자동으로 만든 연결과 모순이 기존 검색 또는 일반적인 RAG보다 가치 있다고 느낀다.

### 1.4 인수 기준 (기획서 3절 검증 기준)

11절에 측정 방법과 함께 상세화한다. 요약:

| ID | 기준 | 유형 |
| --- | --- | --- |
| AC-1 | 문서 100개 Import 완료율 95% 이상 | 자동 |
| AC-2 | 수동 분류 없이 핵심 주제 구조 생성 | 자동 |
| AC-3 | 제안 연결의 70% 이상이 유용 | 사용자 평가 |
| AC-4 | 주요 답변에서 근거 페이지·원본 위치 추적 가능 | 자동 |
| AC-5 | 의도적 모순의 80% 이상 탐지 | 자동 |
| AC-6 | 테스트 사용자 절반 이상이 2주 후 재사용 | 사용자 평가 |
| AC-7 | 사용자 다수가 기존 검색보다 유용하다고 평가 | 사용자 평가 |

## 2. 제품 원칙 — 요구사항의 상위 제약 (기획서 5절)

아래 10개 원칙은 개별 요구사항보다 **상위 제약**이다. 어떤 요구사항도 이를 위반할 수 없으며, 위반하는 설계는 검토에서 거부한다.

| ID | 원칙 | 요구사항에 대한 구속력 |
| --- | --- | --- |
| PR-1 | 원본 불변 | 수집한 원본을 덮어쓰는 기능을 만들 수 없다. 재수집은 항상 새 버전 |
| PR-2 | AI 작성 우선 | 의미 있는 위키 작성·재구성의 기본 주체는 AI. 사용자 직접 편집은 예외 경로 |
| PR-3 | 사용자 통제 | 모든 AI 변경은 승인·거절·보류·수정 요청이 가능해야 한다 |
| PR-4 | 근거 추적 | 주요 주장과 종합은 원본 근거까지 추적 가능해야 한다 |
| PR-5 | 상태 구분 | 5종 지식 상태를 데이터·UI 양쪽에서 구분해야 한다 |
| PR-6 | 연결 중심 | 문서 수가 아니라 관계·흐름 품질이 성공 지표다 |
| PR-7 | 목적 적응 | 동일 원본도 도서관 목적에 따라 다르게 컴파일되어야 한다 |
| PR-8 | 소유권 보장 | 모든 사용자 데이터는 범용 형식으로 내보낼 수 있어야 한다 |
| PR-9 | 안전한 기본값 | 비공개가 기본. 도서관 간 참조도 명시적 허용이 필요하다 |
| PR-10 | 점진적 개인화 | 온보딩은 짧게. 개인화는 사용 중 축적으로 정교해진다 |

**FR-ING-04와 FR-ING-05가 함께 지켜져야 한다.** 승인 없이 비용이 발생하면 안 되고(04), 문서 하나가 막혀 전체가 멈춰서도 안 된다(05).

**FR-ING-26은 기획서 20절 목록에 없다.** 기획서가 나열한 8종은 정상 흐름의 진행 단계이며 운영 중 필요한 두 상태가 빠져 있다. 근거는 다음과 같다.

- `취소됨` — 사용자가 대량 Import를 중단할 수단이 없으면 FR-ING-03(사전 비용 제시)의 의미가 약해진다. 계획 승인 후 마음이 바뀐 사용자가 처리를 멈출 수 있어야 한다.
- `처리량 보류` — FR-ING-22가 "작업을 보류하고 추가 구매를 안내한다"고 요구하는데, 보류를 표현할 상태가 없으면 `실패`로 기록되어 재개할 수 없다. 실패와 보류는 사용자에게 다른 의미다.

두 상태는 정상 흐름 8종과 **동급이 아니다.** 어느 단계에서든 진입할 수 있는 부수 상태이며, `처리량 보류`는 구매 후 원래 단계로 복귀한다.

pm은 이를 **기획서 20절 내부 불일치의 명확화**로 판정했다 — `취소됨`은 API 명세 6.1절에 `/cancel` 엔드포인트가 이미 있어 기능 추가가 아닌 기존 기능의 상태 표현이고, `처리량 보류`는 같은 절에 "작업 보류"가 이미 명시되어 있다. **2026-07-29 사용자 승인**으로 확정되었고 기획서 20절에 반영되었다.

| 큐 | PostgreSQL 기반 작업 큐. API 서버와 Worker는 별도 프로세스 |
| 파일 | S3 호환 객체 스토리지 |
| 프론트엔드 | Next.js, TypeScript, 반응형 웹, Markdown 렌더러, diff 뷰어, 그래프 시각화 |
| 클라우드 | Railway 또는 단일 VPS / 관리형 PostgreSQL / Cloudflare R2 등 |

### 7.2 금지 스택 (기획서 20절)

**Redis / Kafka / Kubernetes / 마이크로서비스 / 전용 벡터 DB.** 필요하다고 판단되면 도입하지 말고 근거와 함께 리더에게 제안한다.

### 7.3 조직 제약

1인 개발 + 초기 소수 사용자. 기획서 24절 8번은 "과도한 MVP 범위"를 리스크로 지목하며, **첫 검증에서 공개·포크보다 개인 도서관의 Ingest 품질을 우선**하도록 정했다. Phase 3(공개)의 요구사항이 Phase 1(개인 코어)보다 먼저 구현되면 이 제약 위반이다.

## 8. 유스케이스 흐름 (주요 3건)

### UC-1: 대량 Import로 도서관 만들기

```
사용자 → 도서관 생성 → 온보딩 질문 5개 응답 → 템플릿 선택 → 운영 헌법 생성
      → Obsidian 저장소 업로드 → [1단계 스캔] → 처리 계획·비용 제시
      → 사용자 승인 → [2단계 처리] → 초안 도서관에 변경 세트 적용
      → 일괄 승인(일반) + 개별 승인(위험) → 새 버전 발행 → 전체 Lint
```

관련: FR-LIB-08~11, FR-INP-01, FR-ING-01~09, FR-CHG-01~05, FR-LNT-01

**실패 경로:** 처리량 부족(FR-ING-22) / 문서별 실패(FR-ING-21) / 맥락 불분명 보류(FR-ING-05) / 민감정보 탐지 차단(NFR-SEC-04)

### UC-2: AI 사서에게 묻고 답변을 지식으로 축적하기

```
사용자 질문 → 현재 도서관 우선 검색 → 근거 충분?
  ├ 예  → 빠른 답변 (출처 숨김) → [근거 보기] → 페이지·원본·신뢰도 노출
  └ 아니오 → 모른다고 명시 → 자료 제안 / 연결 도서관 확장 제안(승인 필요)
                            / 웹 검색 승인 요청
→ 재사용 가치 있는 답변 → 저장 제안(연결·근거·영향 페이지 표시) → 사용자 승인 → 위키 반영
```

관련: FR-ASK-01~11, FR-LIB-06~07, FR-SCH-01~04

**이 흐름의 마지막 두 단계가 P-4를 해결한다.** 저장 제안이 없으면 RAG와 구별되지 않는다.

### UC-3: 페이지 공개와 포크 (Phase 3)

```
사용자 → 페이지 공개 요청 → 공개 전 안전 검사(민감정보·비밀·기밀·원문 과다 재현)
      → 사용자가 출처와 검사 결과 최종 확인 → 포크 허용 여부 설정
      → 특정 페이지 버전 고정 발행
타 사용자 → 공개 페이지 열람 → 포크 → 내 도서관 목적에 맞게 재구성
         → 원본 업데이트 알림 → diff 확인 → 선택적 반영
```

관련: FR-PUB-01~11, FR-LNT-03, NFR-SEC-07
