# 에이전트 팀 운영 가이드

작성일: 2026-07-27
상태: 실험적 기능(Claude Code v2.1.178+ 기준) 정리
출처: https://code.claude.com/docs/ko/agent-teams

## 1. 개념

에이전트 팀은 여러 Claude Code 인스턴스를 하나의 팀으로 묶어 조율하는 기능이다. 메인 세션이 **리더**가 되어 작업을 나누고 결과를 종합하며, **팀원**은 각자 독립된 컨텍스트 윈도우를 가진 별도 Claude Code 세션으로 동작한다.

핵심 차이는 팀원끼리 서로 직접 메시지를 주고받을 수 있다는 점이다. 서브에이전트는 메인 에이전트에게만 결과를 보고하지만, 팀원은 공유 작업 목록을 통해 스스로 조율하고 서로의 결론에 반박할 수 있다. 사용자도 리더를 거치지 않고 개별 팀원과 직접 대화할 수 있다.

### 1.1 서브에이전트와의 비교

| 항목 | 서브에이전트 | 에이전트 팀 |
| --- | --- | --- |
| 컨텍스트 | 자체 윈도우, 결과는 호출자에게 반환 | 자체 윈도우, 완전 독립 |
| 통신 | 메인 에이전트에게만 보고 | 팀원 간 직접 메시지 |
| 조율 | 메인 에이전트가 전부 관리 | 공유 작업 목록 기반 자체 조율 |
| 최적 용도 | 결과만 중요한 집중 작업 | 논의와 협업이 필요한 복잡 작업 |
| 토큰 비용 | 낮음(결과가 요약되어 회수) | 높음(팀원 수에 비례해 선형 증가) |

결과만 받으면 되는 빠른 작업은 서브에이전트, 발견을 공유하고 서로 검증해야 하는 작업은 에이전트 팀을 쓴다.

## 2. 활성화 상태

기본적으로 비활성이며 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 환경변수로 켠다. 이 환경변수가 없으면 팀 디렉터리 자체가 생성되지 않고 Claude가 팀원을 만들거나 제안하지도 않는다.

이 머신에서는 전역 설정 `~/.claude/settings.json`에 이미 적용되어 있어 모든 프로젝트에서 사용 가능하다.

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

v2.1.178부터 별도의 팀 생성 단계가 없어졌다. `TeamCreate` / `TeamDelete` 도구는 제거되었고, 첫 팀원이 스폰되는 순간 팀이 형성되며 세션 종료 시 자동 정리된다. Agent 도구의 `team_name` 입력은 받아들여지지만 무시된다.

## 3. 언제 쓰는가

병렬 탐색이 실질적 가치를 만드는 작업에 쓴다.

- **연구·검토**: 여러 팀원이 문제의 다른 측면을 동시에 조사한 뒤 발견을 공유하고 서로 반박
- **신규 모듈·기능**: 팀원이 각각 다른 파일을 소유해 서로 간섭하지 않음
- **경쟁 가설 디버깅**: 여러 이론을 병렬 검증해 원인에 빠르게 수렴
- **계층 간 조율**: 프론트엔드·백엔드·테스트를 각기 다른 팀원이 소유

반대로 순차 작업, 같은 파일을 고치는 작업, 의존성이 많은 작업은 단일 세션이나 서브에이전트가 낫다. 팀은 조율 오버헤드와 토큰 비용을 함께 늘린다.

## 4. 사용법

### 4.1 팀 시작

자연어로 원하는 작업과 팀원 구성을 설명하면 리더가 공유 작업 목록을 채우고 팀원을 스폰한다.

```text
TODO 주석을 코드베이스 전반에서 추적하는 CLI 도구를 설계 중이다.
세 명의 팀원을 스폰해서 서로 다른 각도로 탐색해라.
한 명은 UX, 한 명은 기술 아키텍처, 한 명은 반대 입장(devil's advocate).
```

Claude는 승인 없이 팀원을 만들지 않는다. 사용자가 요청하거나, Claude가 제안하고 사용자가 확인하는 두 경로만 있다.

### 4.2 팀원 및 모델 지정

수와 모델을 명시할 수 있다.

```text
4명의 팀원을 스폰해서 이 모듈들을 병렬 리팩터링해라. 각 팀원은 Sonnet을 써라.
```

팀원은 리더의 `/model` 선택을 기본 상속하지 않는다. 프롬프트에서 지정하지 않을 때의 기본값은 `/config`의 **기본 팀원 모델**에서 바꾼다. **기본값(리더의 모델)** 을 고르면 리더 모델을 따른다. 노력 수준(effort level)은 리더 것을 상속한다.

### 4.3 서브에이전트 정의 재사용

프로젝트·사용자·플러그인·CLI 어느 범위의 서브에이전트 타입이든 팀원으로 쓸 수 있다. 역할을 한 번 정의해 위임용 서브에이전트와 팀원 양쪽에 재사용하는 방식이다.

```text
security-reviewer 에이전트 타입으로 팀원을 스폰해서 auth 모듈을 감사해라.
```

팀원은 해당 정의의 `tools` 허용 목록과 `model`을 따르고, 정의 본문은 시스템 프롬프트에 **추가**된다(대체가 아님). `SendMessage`와 작업 관리 도구는 `tools`가 제한적이어도 항상 사용 가능하다.

주의: 서브에이전트 정의의 `skills`, `mcpServers` frontmatter는 팀원으로 실행될 때 적용되지 않는다. 팀원은 일반 세션처럼 프로젝트·사용자 설정에서 스킬과 MCP 서버를 로드한다.

### 4.4 계획 승인 요구

위험한 작업은 팀원이 구현 전에 계획을 세우도록 강제할 수 있다. 팀원은 리더가 승인할 때까지 읽기 전용 계획 모드로 동작한다.

```text
auth 모듈 리팩터링용 아키텍트 팀원을 스폰해라.
변경 전에 계획 승인을 요구해라.
```

거부되면 팀원은 계획 모드에 머물러 피드백을 반영해 재제출한다. 리더가 자율적으로 승인을 판단하므로, "테스트 커버리지를 포함한 계획만 승인" 같은 기준을 프롬프트에 명시해 판단에 개입한다.

### 4.5 작업 할당과 요청

공유 작업 목록은 대기 중 / 진행 중 / 완료됨 세 상태를 가지며, 작업 간 의존성을 설정할 수 있다. 미해결 의존성이 있는 대기 작업은 요청되지 않는다.

- **리더 할당**: 어떤 작업을 누구에게 줄지 리더에게 지시
- **자체 요청**: 팀원이 작업을 마치면 다음 미할당·미차단 작업을 스스로 집음

작업 요청은 파일 잠금을 써서 동시 요청 경합을 막는다. 선행 작업이 끝나면 차단된 작업은 자동으로 풀린다.

### 4.6 팀원과 직접 대화

각 팀원은 완전한 독립 세션이므로 직접 지시·질문·방향 전환이 가능하다.

In-process 모드(기본)에서 프롬프트 입력 아래 에이전트 패널을 쓴다.

| 키 | 동작 |
| --- | --- |
| ↑ / ↓ | 팀원 선택 |
| Enter | 선택한 팀원의 대화 기록 열기 및 직접 메시지 |
| Escape | 선택한 팀원의 현재 턴 중단 |
| x | 선택한 팀원 중지 |
| Ctrl+T | 작업 목록 토글 |

팀원을 보는 중에는 일반 텍스트와 스킬이 그 팀원에게 전달되지만, 내장 명령은 여전히 리더 세션에서 실행된다. 팀원의 모델과 fast 모드는 스폰 시점에 고정되므로 `/model`과 `/fast`는 리더에만 적용된다. `/effort`는 보고 있는 팀원의 이후 턴에 적용된다.

### 4.7 팀원 종료

이름으로 지목해 종료를 요청한다.

```text
researcher 팀원에게 종료를 요청해라
```

팀원은 수락해 우아하게 종료하거나 사유와 함께 거부할 수 있다. 팀 공유 디렉터리는 세션 종료 시 자동 정리되므로 별도 뒷정리 단계는 없다.

## 5. 표시 모드

| 모드 | 설명 | 요구사항 |
| --- | --- | --- |
| `in-process` (기본) | 모든 팀원이 메인 터미널 내에서 실행, 에이전트 패널로 전환 | 없음 |
| `tmux` | 팀원마다 분할 창, 터미널에 따라 tmux/iTerm2 자동 감지 | tmux 또는 iTerm2 |
| `iterm2` | iTerm2 네이티브 분할 창 (v2.1.186+) | `it2` CLI + Python API 활성화 |
| `auto` | tmux 세션 안이거나 iTerm2면 분할 창, 아니면 in-process 폴백 | 상동 |

```json
{ "teammateMode": "auto" }
```

단일 세션만 바꾸려면 `claude --teammate-mode auto`.

**이 프로젝트 환경(Windows 11 + Windows Terminal)에서는 분할 창 모드를 쓸 수 없다.** 분할 창은 VS Code 통합 터미널, Windows Terminal, Ghostty에서 지원되지 않으므로 기본값 `in-process`를 그대로 유지하고 에이전트 패널로 팀원을 오간다.

v2.1.199부터 유휴 팀원 행은 다른 팀원이 작업 중인 동안 패널에 남는다. 패널 전체가 유휴가 되면 30초 뒤 숨겨지고 다음 턴에 다시 나타난다. 숨겨진 상태에서도 팀원은 계속 실행되며 이름으로 주소 지정 가능하다. 유휴 팀원이 3명을 넘으면 초과분은 `N idle agents` 한 줄로 접히고 Enter로 펼친다.

## 6. 아키텍처

| 구성 요소 | 역할 |
| --- | --- |
| 팀 리더 | 팀원을 스폰하고 작업을 조율하는 메인 세션 |
| 팀원 | 할당 작업을 수행하는 별도 Claude Code 인스턴스 |
| 작업 목록 | 팀원이 요청·완료하는 공유 작업 항목 |
| 메일박스 | 에이전트 간 메시징 시스템 |

팀 이름은 세션에서 파생되며 `session-` + 세션 ID 앞 8자 형식이다.

| 경로 | 내용 | 수명 |
| --- | --- | --- |
| `~/.claude/teams/{team-name}/config.json` | 팀 구성(`members` 배열: 이름, 에이전트 ID, 타입) | 세션 종료 시 제거 |
| `~/.claude/teams/{team-name}/inboxes/{agent-name}.json` | 에이전트별 메일박스 | 세션 종료 시 제거 |
| `~/.claude/tasks/{team-name}/` | 작업 목록 | 로컬 유지, 업로드 안 됨, `cleanupPeriodDays` 적용 |

작업 목록이 유지되므로 재개된 세션은 작업을 그대로 갖는다.

팀 구성은 세션 ID와 tmux 창 ID 같은 런타임 상태를 담으므로 **직접 편집하거나 미리 작성하지 않는다.** 다음 상태 갱신에서 덮어써진다. 재사용 가능한 역할이 필요하면 서브에이전트 정의를 쓴다(4.3 참조).

프로젝트 수준 팀 구성은 존재하지 않는다. `.claude/teams/teams.json` 같은 파일은 구성으로 인식되지 않고 일반 파일로 취급된다.

메일박스 파일은 읽을 때마다 항목이 검증되며, 형식이 맞지 않는 항목은 오류로 보고되고 제거된다. 유효한 메시지는 그대로 전달된다.

## 7. 권한

팀원은 리더의 권한 설정으로 시작한다. 리더가 `--dangerously-skip-permissions`로 실행되면 팀원도 마찬가지다. 스폰 후 개별 팀원 모드는 바꿀 수 있지만 스폰 시점에 팀원별 모드를 지정할 수는 없다.

`SendMessage`로 전달된 메시지는 수신 에이전트에게 "사용자가 아닌 다른 Claude 세션에서 온 것"으로 알려진다. 따라서:

- 팀원은 권한 프롬프트를 승인하거나 사용자를 대신해 동의할 수 없다.
- 작업이 거부된 팀원이 다른 팀원에게 넘겨 확인을 우회할 수 없다.
- 자동 모드에서 분류기는 다른 에이전트가 전달한 승인 주장을 신뢰할 수 없는 입력으로 취급한다.

팀원의 권한 프롬프트는 리더 세션으로 올라오므로 거기서 승인한다. 계획 승인은 설계된 예외로, 리더가 사용자에게 별도 프롬프트 없이 팀원 계획을 승인한다.

## 8. 컨텍스트와 통신

팀원은 스폰 시 일반 세션과 동일한 프로젝트 컨텍스트(CLAUDE.md, MCP 서버, 스킬)와 리더의 스폰 프롬프트를 받는다. **리더의 대화 기록은 전달되지 않는다.**

정보 공유 경로는 넷이다.

- **자동 메시지 전달**: 팀원이 보낸 메시지는 수신자에게 자동 전달되며, 리더가 폴링할 필요가 없다.
- **유휴 알림**: 팀원이 끝나 멈추면 리더에게 자동 통지된다. v2.1.198부터는 API 오류로 턴이 끝난 경우 정상 완료처럼 보이지 않고 실패 사실과 오류 텍스트를 함께 알린다.
- **공유 작업 목록**: 모든 에이전트가 작업 상태를 보고 요청할 수 있다.
- **팀원 메시징**: 이름으로 특정 팀원 한 명에게 보낸다. 브로드캐스트는 없으므로 전원에게 알리려면 각각 한 통씩 보낸다.

이름은 리더가 스폰 시 할당한다. 이후 프롬프트에서 참조하려면 스폰 지시에서 각 팀원의 이름을 직접 지정하는 편이 예측 가능하다.

## 9. Hooks로 품질 게이트 적용

| Hook | 시점 | 종료 코드 2의 효과 |
| --- | --- | --- |
| `TeammateIdle` | 팀원이 유휴로 전환하려 할 때 | 피드백을 보내고 계속 작동시킴 |
| `TaskCreated` | 작업 생성 시 | 생성을 막고 피드백 전달 |
| `TaskCompleted` | 작업 완료 표시 시 | 완료를 막고 피드백 전달 |

`TaskCreated` / `TaskCompleted` / `TeammateIdle` 페이로드의 `team_name` 필드는 세션 파생 이름을 전달하며 더 이상 사용되지 않는다(deprecated).

## 10. 모범 사례

1. **충분한 컨텍스트를 준다.** 팀원은 리더 대화 기록을 상속하지 않으므로 작업별 세부 사항을 스폰 프롬프트에 넣는다.

   ```text
   보안 리뷰어 팀원을 다음 프롬프트로 스폰해라: "src/auth/의 인증 모듈을
   보안 취약점 관점에서 검토해라. 토큰 처리, 세션 관리, 입력 검증에 집중해라.
   앱은 httpOnly 쿠키에 저장된 JWT를 쓴다. 발견한 문제를 심각도와 함께 보고해라."
   ```

2. **팀 크기는 3~5명으로 시작한다.** 하드 제한은 없지만 토큰 비용은 선형 증가하고 조율 오버헤드와 충돌 가능성도 함께 늘어 수익이 체감한다. 집중된 3명이 산만한 5명보다 나은 경우가 많다.

3. **팀원당 5~6개 작업을 유지한다.** 독립 작업이 15개면 3명이 좋은 출발점이다. 작업이 부족하면 리더에게 더 잘게 쪼개라고 요청한다.

4. **작업 크기를 맞춘다.** 너무 작으면 조율 오버헤드가 이득을 넘고, 너무 크면 체크인 없이 오래 돌아 헛수고 위험이 커진다. 함수·테스트 파일·리뷰처럼 명확한 결과물을 내는 자체 완결 단위가 적절하다.

5. **파일 충돌을 피한다.** 두 팀원이 같은 파일을 편집하면 덮어쓰기가 발생한다. 팀원마다 서로 다른 파일 집합을 소유하도록 나눈다.

6. **리더가 먼저 손대면 멈춘다.** 리더가 위임 대신 직접 구현하기 시작하면 이렇게 지시한다.

   ```text
   진행하기 전에 팀원들이 작업을 마칠 때까지 기다려라
   ```

7. **연구·검토부터 시작한다.** 처음이라면 PR 리뷰, 라이브러리 조사, 버그 조사처럼 코드를 쓰지 않고 경계가 뚜렷한 작업으로 시작해 병렬 구현의 조율 문제를 피한다.

8. **모니터링하고 조율한다.** 무인으로 오래 돌릴수록 헛수고 위험이 커진다.

## 11. 사용 사례 예시

### 11.1 병렬 코드 리뷰

단일 리뷰어는 한 가지 유형의 문제로 기울기 마련이다. 리뷰 기준을 독립 도메인으로 쪼개면 겹침 없이 각 영역이 동시에 철저한 주의를 받는다.

```text
PR #142를 검토하기 위해 세 명의 팀원을 배치한다:
- 보안 영향에 중점을 두는 팀원
- 성능 영향을 확인하는 팀원
- 테스트 커버리지를 검증하는 팀원
각각 검토하고 발견 사항을 보고하도록 한다.
```

### 11.2 경쟁 가설 조사

단일 에이전트는 그럴듯한 설명 하나를 찾고 멈춘다. 팀원을 명시적으로 적대적으로 만들면 앵커링을 막을 수 있다.

```text
사용자들이 앱이 연결 상태를 유지하는 대신 한 메시지 후에 종료된다고 보고한다.
5명의 에이전트 팀원을 배치해 서로 다른 가설을 조사하게 한다. 그들이 서로 대화하며
과학적 토론처럼 서로의 이론을 반박하려고 하게 한다. 발견 사항 문서를
합의가 형성되는 대로 갱신한다.
```

여러 독립 조사자가 서로의 이론을 적극적으로 반박할 때, 살아남은 이론이 실제 근본 원인일 확률이 훨씬 높다.

## 12. 문제 해결

| 증상 | 대응 |
| --- | --- |
| 팀원이 안 보임 | 에이전트 패널을 ↑↓로 확인한다. 유휴 행은 중지가 아니라 숨김이며 이름으로 메시지를 보내면 다시 나타난다. 작업이 팀을 쓸 만큼 복잡한지도 확인한다. |
| 분할 창이 안 열림 | `which tmux`로 설치·PATH를 확인한다. iTerm2면 `it2` CLI와 Python API 활성화를 확인한다. Windows Terminal에서는 애초에 미지원이다. |
| 권한 프롬프트가 과다 | 팀원 스폰 전에 권한 설정에서 흔한 작업을 사전 승인한다. |
| 팀원이 오류에서 멈춤 | 패널에서 해당 팀원을 열어 출력을 확인하고 직접 지시하거나 대체 팀원을 스폰한다. v2.1.198부터 리더나 다른 팀원의 메시지가 API 재시도 대기 중인 in-process 팀원을 깨워 즉시 재시도시킨다. |
| 리더가 작업 완료 전 종료 | 계속하라고 지시한다. 위임 없이 직접 시작했다면 팀원을 기다리라고 지시한다. |
| 고아 tmux 세션 | `tmux ls`로 확인 후 `tmux kill-session -t <session-name>`으로 정리한다. |

## 13. 알려진 제한 사항

- **In-process 팀원은 세션 재개가 안 된다.** `/resume`과 `/rewind`는 팀원을 복원하지 않는다. 재개 후 리더가 없는 팀원에게 메시지를 보내려 하면 새 팀원을 스폰하라고 지시한다.
- **작업 상태가 지연될 수 있다.** 팀원이 완료 표시를 놓쳐 의존 작업을 막을 수 있다. 실제 완료 여부를 확인하고 상태를 수동 갱신하거나 리더에게 팀원을 재촉시킨다.
- **종료가 느릴 수 있다.** 팀원은 현재 요청이나 도구 호출을 마친 뒤 종료된다.
- **세션당 팀 하나.** 추가 명명 팀을 만들거나 세션 간 팀을 공유할 수 없다.
- **중첩 팀 없음.** 팀원은 자기 팀원을 스폰할 수 없다. 리더만 팀을 관리한다.
- **In-process 팀원의 백그라운드 서브에이전트 불가.** `run_in_background` 또는 정의의 `background: true`는 오류를 반환한다. 팀원의 백그라운드 작업이 리더 프로세스보다 오래 살 수 없기 때문이다. 메인 대화에서 시작한 서브에이전트는 평소 기본값을 따른다.
- **리더 고정.** 메인 세션이 수명 내내 리더다. 리더십 이전이나 팀원 승격은 불가능하다.
- **권한은 스폰 시점 고정.** 스폰 후 개별 변경만 가능하다.
- **분할 창은 tmux 또는 iTerm2 필요.** VS Code 통합 터미널, Windows Terminal, Ghostty에서는 미지원이다.

`CLAUDE.md`는 정상 동작한다. 팀원은 작업 디렉터리의 `CLAUDE.md`를 읽으므로 전 팀원 공통 지침은 여기에 둔다.

## 14. 이 프로젝트에서의 적용 지침

ZeroWiki 기준으로 팀이 유효한 시점과 구성 예시를 정리한다.

| 상황 | 구성 |
| --- | --- |
| ERD·API 명세 교차 검증 | 3명 — 데이터 모델 정합성 / API 계약 정합성 / 기획서 대비 누락 점검 |
| Ingest·Lint 파이프라인 설계 | 3명 — 큐/작업 상태 모델 / AI 호출 비용·실패 처리 / 관측성 및 재시도 |
| Phase 1 코어 구현 | 계층별 소유 — 스키마·마이그레이션 / API 핸들러 / 테스트 |
| 단순 문서 수정, 단일 파일 리팩터링 | 팀 미사용. 단일 세션 또는 서브에이전트 |

운영 시 유의할 점:

- 표시 모드는 `in-process` 고정이다(5절).
- 스폰 프롬프트에 관련 기획 문서 경로(`docs/ZeroWiki-ERD-초안.md` 등)를 명시한다. 팀원은 리더의 대화 기록을 못 받으므로 어떤 문서를 읽어야 하는지 직접 알려줘야 한다.
- 스키마와 API 명세를 동시에 고치는 작업은 파일 소유를 갈라 배정한다(10.5).
- 팀원 이름을 스폰 시 직접 지정해 두면 이후 프롬프트에서 지목하기 쉽다.
