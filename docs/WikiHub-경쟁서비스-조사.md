# WikiHub 경쟁 서비스 조사

조사일: 2026-07-26  
조사 대상: [wikihub.md](https://wikihub.md/)

## 1. 결론

WikiHub는 ZeroWiki와 같은 LLM Wiki 흐름을 지원하지만, 현재 제품의 중심은 **AI가 개인 자료를 자동으로 지식화하는 서비스**보다 **Markdown 위키를 Git·API·MCP로 호스팅하고 공개·포크하는 플랫폼**에 가깝다.

간단히 구분하면 다음과 같다.

- **WikiHub:** LLM 위키를 위한 GitHub
- **ZeroWiki:** 개인 자료를 목적별 도서관으로 컴파일하고 관리하는 AI 사서

기능 일부는 강하게 겹치지만 핵심 고객 경험은 다르다. WikiHub는 개발자와 외부 AI 에이전트가 위키를 이미 만들 수 있다고 전제한다. ZeroWiki는 일반 사용자가 자료만 제공해도 서비스 내부 AI가 도서관 설계, Ingest, 연결, 모순, 승인, Lint까지 수행하는 관리형 제품을 지향한다.

## 2. WikiHub가 제공하는 것

공식 사이트와 공개 저장소에서 확인한 기능은 다음과 같다.

### Markdown 위키 호스팅

- `.md` 파일, 폴더, ZIP 업로드
- Git push로 배포
- 위키링크
- KaTeX 수식
- 코드 문법 강조
- 각주
- Obsidian 이미지 임베드 렌더링

출처: [WikiHub 홈페이지](https://wikihub.md/)

### 실제 Git 저장소

각 위키가 실제 Git 저장소다.

- clone
- push
- branch
- blame
- 전체 버전 이력
- 언제든 복제해 이탈 가능

공개 저장소 설명에 따르면 위키마다 소유자용 원본 저장소와 공개 콘텐츠용 파생 저장소를 분리한다. Git이 콘텐츠의 기준이고 PostgreSQL은 메타데이터, 검색 인덱스, 소셜 그래프를 저장한다.

출처: [WikiHub 공개 저장소](https://github.com/tmad4000/wikihub)

### 페이지별 접근 제어

페이지마다 다음 공개 범위를 설정할 수 있다.

- public
- private
- unlisted
- shared
- public-edit

`.wikihub/acl` 파일의 glob 패턴 또는 페이지 frontmatter로 접근 권한을 관리한다.

### 에이전트 우선 API

- REST API
- MCP 서버
- CLI
- `llms.txt`
- Markdown content negotiation
- API 키 기반 에이전트 접근

Claude Code, Cursor, ChatGPT 같은 외부 AI 클라이언트가 위키를 직접 읽고 쓸 수 있다. 계정 생성부터 위키와 페이지 생성까지 브라우저 없이 API 호출만으로 수행할 수 있다.

출처: [WikiHub 에이전트 문서](https://wikihub.md/agents)

### 소셜 기능

- 공개 위키 탐색
- 사용자 프로필
- star
- fork
- 원본에 편집 제안
- 페이지별 공유

### 검색

- 공개 위키 전체 검색
- 개인 비공개 페이지 검색
- `Cmd+K` 중심 전문 검색

## 3. LLM Wiki 지원 방식

WikiHub는 `structured`와 `freeform` 템플릿을 제공한다. structured 템플릿은 `raw/`, `wiki/`, `schema.md`와 ingest/query/lint 규칙을 에이전트가 따르도록 안내한다.

그러나 공개된 제품 설명상 WikiHub 자체가 다음 작업을 완전한 관리형 파이프라인으로 제공한다고 보기는 어렵다.

- PDF·Notion·웹 자료의 자동 수집과 파싱
- 사용자 목적 인터뷰
- 대량 문서 Ingest 계획과 비용 승인
- 연결 및 모순 변경 세트 생성
- 위험 변경만 추려 승인받는 UI
- 분야별 지식 노후화 검사
- 내장 AI 사서 대화
- 사용량 기반 LLM 처리 요금제

대신 외부 AI 에이전트가 WikiHub의 `schema.md`를 읽고 ingest/query/lint 작업을 수행한 뒤 결과를 WikiHub에 저장하는 구조다.

즉, WikiHub는 **에이전트가 사용할 수 있는 위키 인프라와 배포 대상**이고, ZeroWiki는 **에이전트 자체와 지식 컴파일 경험을 제품으로 제공**하려 한다.

## 4. ZeroWiki와의 기능 비교

| 영역 | WikiHub | ZeroWiki 기획 |
| --- | --- | --- |
| 핵심 포지션 | LLM 위키 호스팅·배포 플랫폼 | 관리형 개인 지식 도서관 |
| 주요 사용자 | 개발자, AI 에이전트 사용자 | 한 분야를 깊게 탐구하는 일반 사용자 |
| 데이터 입력 | Markdown, ZIP, Git push, API | Obsidian, 파일, Notion, 웹 클리핑 |
| 위키 생성 | 외부 에이전트가 작성 | 서비스 내 AI가 자동 컴파일 |
| 개인 맥락 | schema 템플릿 중심 | 5문항 온보딩 + 점진적 운영 헌법 |
| 여러 위키 | 지원 | 지원 |
| 공통 원본 보관소 | 확인되지 않음 | 계정 공통 원본을 여러 도서관이 참조 |
| 도서관 간 참조 | 확인되지 않음 | 명시적 단방향 참조 |
| 연결 발견 | 외부 에이전트 책임 | 제품 핵심 기능 |
| 모순 탐지 | 스키마가 에이전트에 지시 | 주장·근거 기반 내장 기능 |
| 변경 승인 | Git 버전과 편집 흐름 | 위험 변경 PR형 승인 |
| Lint | 외부 에이전트 워크플로 | 대량 Ingest 후·월간 자동 Lint |
| AI 대화 | MCP로 외부 ChatGPT 등에 연결 | 제품 내 AI 사서 |
| Git 소유권 | 실제 Git 저장소가 기준 | DB 기준 + Markdown/Git 내보내기 |
| 페이지 공개 | 세밀한 ACL | MVP는 개별 페이지 공개 |
| 포크·제안 | 지원 | MVP 지원 예정 |
| 과금 | 현재 무료로 안내 | 월 구독 + 월 처리량 |

## 5. WikiHub가 더 앞선 부분

### 5.1 Git 네이티브 소유권

“내 데이터는 내가 언제든 가져갈 수 있어야 한다”는 약속을 가장 직접적으로 구현했다. 실제 Git clone이 가능하므로 잠금 효과가 작고 개발자 신뢰를 얻기 쉽다.

ZeroWiki는 Git을 주 데이터베이스로 쓰지 않더라도 다음 수준을 목표로 해야 한다.

- 전체 Markdown 저장소 내보내기
- 안정적인 경로와 frontmatter
- 변경 diff와 버전
- 이후 GitHub 자동 미러링
- 내보낸 자료를 다시 Import할 수 있는 왕복 가능성

### 5.2 에이전트 친화성

REST, MCP, CLI, `llms.txt`, Markdown 응답을 처음부터 함께 제공한다. 외부 에이전트가 별도 UI 없이도 모든 핵심 작업을 할 수 있다.

ZeroWiki도 장기적으로 MCP API를 제공하면 다음 장점이 있다.

- Codex나 Claude가 ZeroWiki를 장기 기억으로 사용
- 사용자가 서비스 UI 밖에서도 도서관을 검색
- 외부 자동화가 원본을 추가
- ZeroWiki가 특정 LLM UI에 종속되지 않음

다만 MVP의 핵심은 비개발자용 제품 경험이므로 MCP는 Phase 1 필수가 아니라 후속 확장으로 두는 것이 적합하다.

### 5.3 접근 제어 모델

페이지별 ACL을 파일로 선언하고 시각 UI에서도 바꿀 수 있다. ZeroWiki MVP는 개별 페이지 공개만 지원하지만 향후 `private / unlisted / public / invited` 정도의 정책 확장에 참고할 가치가 있다.

### 5.4 공개 생태계

공개 위키 탐색, star, fork, 편집 제안이 이미 하나의 네트워크를 형성한다. ZeroWiki도 공개 기능을 만들 때 단순 공유 링크를 넘어 다음 계보를 보존해야 한다.

- 누구의 어느 버전에서 포크했는가
- 내 도서관에서 어떻게 재해석했는가
- 원본이 이후 어떻게 바뀌었는가
- 변경분을 선택적으로 가져올 수 있는가

## 6. ZeroWiki가 차별화할 부분

### 6.1 관리형 AI 사서

사용자가 AGENTS.md, API 키, Git, MCP를 이해할 필요가 없어야 한다. 사용자는 도서관 목적을 답하고 자료를 넣고 위험 변경만 판단한다.

### 6.2 공통 원본과 목적별 컴파일

같은 원본을 여러 도서관에서 서로 다르게 해석하는 모델은 WikiHub의 “위키 저장소”보다 한 단계 위의 개인 지식 운영 모델이다.

### 6.3 연결과 모순의 품질

ZeroWiki의 핵심 경쟁력은 페이지 렌더링이나 Git 호스팅이 아니라 다음 품질이다.

- 왜 두 지식이 연결되는지 설명
- 단순 유사성과 의미 있는 관계 구분
- 시간 변화, 적용 조건 차이, 관점 차이와 진짜 모순 구분
- 사용자의 거절 사유를 이후 판단에 반영

### 6.4 승인 피로 최소화

AI 자동화와 사용자 통제를 동시에 달성해야 한다.

- 안전한 변경은 일괄 승인
- 사실 수정·삭제·모순 같은 위험 변경만 개별 승인
- 변경의 근거와 영향을 먼저 표시

### 6.5 분야별 유지보수

도서관 템플릿이 지식의 분류뿐 아니라 노후화 판단까지 결정한다.

- 개발: 버전과 공식 문서
- 연구·건강: 최신 연구와 가이드라인
- 개인 의사결정: 사용자의 경험과 판단 변화

## 7. WikiHub에서 직접 참고할 설계

1. URL 자체가 사람과 에이전트 모두에게 이해 가능한 구조
2. Markdown content negotiation
3. API 키와 MCP 기반 에이전트 접근
4. Git clone 가능한 탈출구
5. 페이지 단위 접근 제어
6. 포크 원본 계보 보존
7. 공개 원본과 비공개 원본 저장소 분리
8. schema 파일을 도서관 운영 헌법의 내보내기 형식으로 활용
9. 비공개 기본값
10. 서버 렌더링 중심의 빠른 문서 열람

## 8. 그대로 따라가면 안 되는 부분

### Git을 유일한 기준으로 삼기

ZeroWiki에는 Git으로 표현하기 어려운 트랜잭션 데이터가 많다.

- 공통 원본을 여러 도서관에서 참조
- 주장과 근거 단위 연결
- 비동기 처리 상태
- 처리량 과금
- 위험 변경 승인
- 알림
- 삭제 유예
- 개인화 피드백

따라서 PostgreSQL을 운영 기준으로 두고 Markdown/Git을 완전한 내보내기 및 미러링 계층으로 제공하는 편이 적합하다.

### 외부 에이전트에 품질을 전적으로 위임하기

외부 에이전트가 schema 지시를 따르는 구조는 유연하지만 결과 품질과 안전성을 서비스가 보장하기 어렵다. ZeroWiki는 Ingest, 모순, 승인, Lint를 제품 내부 워크플로로 통제해야 한다.

### 초기에 과도한 공개 ACL 제공

ZeroWiki는 민감한 개인·업무 자료를 다룬다. MVP에서는 비공개 도서관과 개별 공개 페이지만 지원하고, 복잡한 파일별 공동 편집 ACL은 뒤로 미루는 것이 안전하다.

## 9. 현재 단계에 대한 관찰

WikiHub는 실제 접속 가능한 서비스이며 공개 위키, Git 저장소, MCP, CLI, API가 작동하는 형태로 소개돼 있다. 공개 사이트는 현재 무료라고 안내한다.

다만 다음 이유로 아직 초기 단계 제품으로 보인다. 이는 공개 자료를 바탕으로 한 추론이다.

- 별도의 유료 가격 체계가 확인되지 않음
- 로드맵이 공개 이슈 목록 중심
- 사이트에 노출된 공개 위키의 사회적 지표가 아직 작음
- 공개 저장소가 빠르게 변경되는 개발 단계
- WikiHub 자체 관리형 AI 처리보다 외부 에이전트 사용법이 중심

공개 자료에서 명확한 서비스 약관, 개인정보 처리방침, 보안·보존 정책은 확인하지 못했다. 민감한 개인 자료를 실제 업로드하기 전에는 운영 주체와 정책을 별도로 확인해야 한다.

## 10. 경쟁 판단

### 단기

직접적인 대체재라기보다 인접 서비스다.

- WikiHub는 이미 만들어진 Markdown 위키의 호스팅과 유통에 강하다.
- ZeroWiki는 원본에서 신뢰할 수 있는 위키를 만드는 과정에 집중한다.

### 중기

WikiHub가 관리형 Ingest와 내장 AI 대화를 추가하거나, ZeroWiki가 공개 위키 네트워크와 MCP를 확장하면 직접 경쟁할 가능성이 높다.

### 전략적 선택지

1. **독립 경쟁:** ZeroWiki가 자체 호스팅·공개·포크까지 모두 제공한다.
2. **상호운용:** ZeroWiki에서 만든 Markdown을 WikiHub에 내보내거나 게시한다.
3. **인프라 참고:** WikiHub의 Git·MCP·ACL 패턴만 참고해 자체 구현한다.

현재 추천은 3번으로 시작하고, 표준 Markdown 내보내기를 통해 2번의 가능성을 열어두는 것이다. WikiHub에 종속되면 ZeroWiki의 공통 원본, 승인, 과금, 개인정보 정책을 통제하기 어렵다.

## 11. 최종 시사점

WikiHub의 존재는 ZeroWiki 아이디어를 약화시키지 않는다. 오히려 다음 수요가 실제로 형성되고 있다는 신호다.

- Markdown 위키의 소유권
- LLM 에이전트가 읽고 쓰는 지식 저장소
- 공개·포크 가능한 지식
- RAG가 아닌 누적형 위키

대신 ZeroWiki의 메시지는 “LLM 위키를 호스팅한다”에 머물면 안 된다.

> ZeroWiki는 파일을 올리는 곳이 아니라, 사용자의 목적을 이해한 AI 사서가 자료를 연결하고 모순을 관리해 살아 있는 개인 도서관으로 바꾸는 서비스다.

이 차별점을 실제로 증명하는 기능은 화려한 그래프가 아니라 **대량 Ingest 계획, 연결 품질, 모순 탐지, 위험 변경 승인, 운영 헌법의 점진적 학습**이다.
