# /brief

**리더가 직접 한다. 팀원을 스폰하지 않는다.** 네 역할의 상태 파일을 리더가 읽고, 교차 대조하고, 종합해 사용자에게 다음 행동을 제안한다.

## 사용법

```text
/brief              전원 (backend, frontend, qa, pm)
/brief backend      특정 역할만
/brief backend qa   여러 역할 지정
```

역할 이름은 `backend`, `frontend`, `qa`, `pm` 중에서만 받는다. 그 밖의 인자가 오면 오타로 보고 사용자에게 되묻는다.

## 왜 리더가 직접 하는가

브리핑은 **상태를 읽는 일**이지 일을 하는 일이 아니다. 팀원을 스폰하면 네 명분의 토큰을 쓰고, 각자 맥락 없이 처음부터 시작하며, 리더는 결국 그 보고를 다시 검증해야 한다. 상태 파일은 리더가 직접 읽으면 되는 분량이다.

대신 리더는 팀원이 대신 해주던 판단을 스스로 져야 한다. 각 역할의 관점에서 파일을 읽되, **자기 요약을 진실로 착각하지 않는다.** 근거는 항상 파일 경로와 절 번호로 남긴다.

## 이 스킬의 성격

**읽기 전용이다.** 어떤 파일도 수정하지 않는다.

`STATE.md`가 현실과 어긋난 것을 발견해도 브리핑 중에 고치지 않는다. **어긋났다는 사실을 보고에 적고, 수정은 해당 역할이 다음에 일할 때 하게 한다.** 상태 파일의 소유자는 각 역할이다(헌법 제1조 1항). 리더가 대신 써넣으면 그 역할은 자기가 무엇을 놓쳤는지 영영 모른다.

## 절차

### 1단계 — 저장소 실제 상태를 잡는다

무엇보다 먼저 확인한다. 상태 파일이 아니라 저장소가 진실이다.

```bash
git log --oneline -10
git status --short
```

각 역할 `STATE.md`의 마지막 갱신일과 최근 커밋 날짜를 대조한다. **STATE가 최근 커밋보다 오래됐으면 그 역할의 기록은 자기가 모르는 변경 위에 서 있다.** 어느 커밋을 놓쳤는지 해시 단위로 특정해 둔다.

### 2단계 — 역할별 파일을 병렬로 읽는다

지정된 역할마다 세 개를 읽는다. 서로 의존하지 않으므로 한 번에 읽는다.

| 읽을 것 | 목적 |
| --- | --- |
| `.claude/team/{역할}/STATE.md` | 그 역할이 스스로 기록한 현재 위치 |
| `.claude/team/{역할}/WORKLOG.md` | 최근 실제로 한 일 — STATE와 대조할 근거 |
| `.claude/team/{역할}/CLAUDE.md` | 그 역할의 책임 경계 — 무엇이 그의 일인지 판정할 기준 |

전원 브리핑이면 `.claude/CONSTITUTION.md`와 `docs/ZeroWiki-요구사항-정의서.md` 12절(미확정 항목·결정 주체 표)도 함께 읽는다. 12절은 2번 판정의 정본이다.

### 3단계 — 역할마다 다섯 가지를 판정한다

읽은 내용을 그대로 옮기지 않는다. 각 역할에 대해 리더가 다음을 **판정**한다.

1. **지금 시작할 수 있는 일** — 차단 요인이 없어 바로 착수 가능한 작업. 없으면 "없음"이라고 적는다.
2. **막혀 있는 일과 해소 주체** — `사용자 결정` / `다른 역할` / `벤치마크` / `리더 확정` 중 하나로 분류한다.
3. **STATE와 현실의 차이** — 1단계에서 특정한 미반영 커밋이 이 역할의 기록에 어떤 구멍을 냈는지. 고치지 말고 적기만 한다.
4. **다른 역할에게 필요한 것** — 누구에게 무엇을 받아야 진행되는지.
5. **우선순위 1순위와 그 이유** — 여러 개를 나열하지 말고 하나를 고른다.

**2번의 분류를 정확히 한다.** 기술 결정을 "사용자 결정 대기"로 올리면 오지 않을 답을 무한정 기다린다. 미확정 항목의 결정 주체는 `docs/ZeroWiki-요구사항-정의서.md` 12절 표가 정본이다. 기억으로 쓰지 말고 열어서 확인한다.

### 4단계 — 종합한다

역할별 판정을 나열하는 것으로 끝내지 않는다. 역할을 가로질러야만 보이는 것을 찾는다.

- **역할 간 의존 사슬** — A가 B를 기다리고 B가 C를 기다리는 구조. 사슬의 맨 끝이 진짜 병목이다.
- **역할 간 모순** — 같은 계약을 backend와 frontend가 다르게 적어 둔 경우. 이건 각 STATE만 봐서는 절대 안 보이고, 전원을 한 번에 읽는 리더만 잡을 수 있다. **가장 중요한 산출물이다.**
- **지금 사용자만 풀 수 있는 것** — 사용자 결정 항목을 한 묶음으로. 하나씩 흩어 물으면 사용자가 맥락을 잃는다.
- **리더가 지금 확정할 수 있는 것** — 기술 결정은 리더가 확정한다. 사용자를 기다리지 않는다.
- **다음 한 걸음** — 선택지를 나열하지 말고 하나를 권고한다. 근거와 함께.

## 검증 의무

읽은 문서의 서술을 무비판적으로 옮기지 않는다(헌법 제4조 8항). 상태 파일에 적힌 것은 **그 역할의 주장**이지 사실이 아니다. 다음은 실제로 겪은 실패이므로 매번 확인한다.

| 확인할 것 | 방법 |
| --- | --- |
| 분량·수치 기록 | `wc -l`, `git diff --stat` 등으로 직접 센다 |
| "완료"라는 서술 | 해당 산출물 파일을 열어 그 내용이 실제로 있는지 본다 |
| 근거 없는 백분율 | 분모가 정의되지 않은 `100%`, `N% 달성` 같은 표현은 거부한다 |
| UD 번호 인용 | `docs/ZeroWiki-요구사항-정의서.md` 12절 표와 대조한다 |
| 요구사항 ID 인용 | 존재하지 않는 ID(`FR-LLM-*` 같은)가 적혀 있는 경우가 있다 |
| 일정·날짜 | 어느 문서에도 없는 일정이 적혀 있는 경우가 있다 |

**"모두 이상 없음" 보고는 그 자체로 의심 신호다.** 무엇을 어떻게 대조했는지 근거가 없으면 검증한 것이 아니라 통과시킨 것이다. 이 의심은 이제 팀원이 아니라 **리더 자신의 요약**을 향한다.

## 팀원 스폰이 필요해지는 경우

브리핑은 스폰하지 않는다. 다만 브리핑 결과 다음이 드러나면, 그건 브리핑의 범위를 넘은 것이므로 **사용자에게 알리고 별도 작업으로 스폰을 제안한다.** 브리핑 안에서 몰래 실행하지 않는다.

- 상태 파일만으로는 판단할 수 없어 해당 영역의 코드·설계를 깊이 파야 할 때
- 역할 간 모순을 해소하려면 당사자의 기술 판단이 필요할 때
- STATE가 크게 어긋나 그 역할이 직접 재정비해야 할 때

## 파일 소유권

이 스킬 파일(`.claude/skills/**`)은 **리더 소유**다(헌법 제1조 4항에 따른 지정, 2026-07-29). 팀원은 읽기만 한다.

브리핑은 읽기 전용이므로 소유권 문제를 일으키지 않는다. 헌법 제1조 1항의 소유권 표는 브리핑 중에도 그대로 적용된다.
