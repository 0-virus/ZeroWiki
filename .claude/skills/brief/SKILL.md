# /brief

각 역할이 자기 `STATE.md`를 읽고 **지금 실제로 시작할 수 있는 일**을 보고한다. 리더가 이를 종합해 사용자에게 다음 행동을 제안한다.

## 사용법

```text
/brief              전원 (backend, frontend, qa, pm)
/brief backend      특정 역할만
/brief backend qa   여러 역할 지정
```

역할 이름은 `backend`, `frontend`, `qa`, `pm` 중에서만 받는다. 그 밖의 인자가 오면 오타로 보고 사용자에게 되묻는다.

## 이 스킬의 성격

**읽기 전용이다.** 브리핑은 상태를 파악하는 것이지 일을 하는 것이 아니다. 팀원이 브리핑 중에 문서를 고치기 시작하면 그건 이미 브리핑이 아니다.

예외는 하나다. **`STATE.md`가 현실과 다르다는 것을 발견하면 그 파일은 고친다.** 자기 상태 기록이 틀린 것을 알고도 두는 것이 더 나쁘다. 그 밖의 파일은 건드리지 않는다.

## 절차

### 1단계 — 리더가 먼저 맥락을 잡는다

팀원을 스폰하기 전에 리더가 직접 확인한다. 이건 팀원에게 물어볼 것이 아니다.

```bash
git log --oneline -10
git status --short
```

그리고 각 역할 `STATE.md`의 마지막 갱신일과 최근 커밋 날짜를 대조한다. **STATE가 최근 커밋보다 오래됐으면 그 역할은 자기가 모르는 변경 위에 서 있다.** 이 사실을 스폰 프롬프트에 담아야 팀원이 헛다리를 짚지 않는다.

### 2단계 — 팀원을 병렬 스폰한다

지정된 역할을 한 번에 스폰한다. 서로 의존하지 않으므로 순차 실행할 이유가 없다.

각 스폰 프롬프트에 반드시 포함할 것:

- 필독 파일 3종 경로 (헌법 → 역할 `CLAUDE.md` → 자기 `STATE.md`)
- **1단계에서 파악한 "네가 모르는 변경"** — 커밋 해시와 바뀐 문서를 구체적으로
- 아래 「팀원이 답해야 하는 것」 5개 항목
- 읽기 전용 제약

팀원은 리더의 대화 기록을 상속하지 않는다. 경로와 절 번호를 항상 명시한다.

### 3단계 — 팀원이 답해야 하는 것

각 역할에게 다음 5개를 요구한다. 순서를 지키게 한다.

1. **지금 시작할 수 있는 일** — 차단 요인이 없어 오늘 바로 착수 가능한 작업. 없으면 "없음"이라고 적는다.
2. **막혀 있는 일과 해소 주체** — 무엇에 막혀 있고 누가 풀어야 하는지. `사용자 결정` / `다른 역할` / `벤치마크` / `리더 확정`으로 구분한다.
3. **STATE와 현실의 차이** — 자기 `STATE.md`가 최근 변경을 반영하는지. 반영하지 못했으면 무엇을 놓쳤는지 적고 STATE를 고친다.
4. **다른 역할에게 필요한 것** — 누구에게 무엇을 받아야 진행되는지.
5. **우선순위 1순위와 그 이유** — 여러 개를 나열하지 말고 하나를 고르게 한다.

**2번의 구분을 정확히 하게 한다.** 기술 결정을 "사용자 결정 대기"로 올리면 답이 오지 않는 것을 무한정 기다린다. 미확정 항목의 결정 주체는 `docs/ZeroWiki-요구사항-정의서.md` 12절 표가 정본이다. 추측하지 말고 열어서 확인하게 한다.

### 4단계 — 리더가 종합한다

팀원 보고를 그대로 옮기지 않는다. 다음을 판단해 사용자에게 제시한다.

- **역할 간 의존 사슬** — A가 B를 기다리고 B가 C를 기다리는 구조. 사슬의 맨 끝이 진짜 병목이다.
- **지금 사용자만 풀 수 있는 것** — 사용자 결정 항목을 한 묶음으로. 하나씩 흩어 물으면 사용자가 맥락을 잃는다.
- **리더가 지금 확정할 수 있는 것** — 기술 결정은 팀원 권고를 받아 리더가 확정한다. 사용자를 기다리지 않는다.
- **다음 한 걸음** — 여러 선택지를 나열하지 말고 하나를 권고한다. 근거와 함께.

## 검증 의무

팀원 보고를 무비판적으로 옮기지 않는다(헌법 제4조 8항). 다음은 실제로 겪은 실패이므로 매번 확인한다.

| 확인할 것 | 방법 |
| --- | --- |
| 분량·수치 보고 | `wc -l`, `git diff --stat` 등으로 직접 센다 |
| "완료"라는 주장 | 해당 파일을 열어 그 내용이 실제로 있는지 본다 |
| 근거 없는 백분율 | 분모가 정의되지 않은 `100%`, `N% 달성` 같은 표현은 거부한다 |
| UD 번호 인용 | `docs/ZeroWiki-요구사항-정의서.md` 12절 표와 대조한다 |
| 요구사항 ID 인용 | 존재하지 않는 ID(`FR-LLM-*` 같은)를 만들어 쓰는 경우가 있다 |
| 일정·날짜 | 어느 문서에도 없는 일정을 지어내는 경우가 있다 |

**"모두 이상 없음" 보고는 그 자체로 의심 신호다.** 무엇을 어떻게 대조했는지 근거가 없으면 검증한 것이 아니라 통과시킨 것이다.

## 비용 판단

전원 스폰은 팀원 4명분의 토큰을 쓴다. 다음 경우에는 스폰하지 말고 리더가 직접 `STATE.md`를 읽는 편이 낫다.

- 마지막 브리핑 이후 아무것도 바뀌지 않았을 때
- 특정 역할의 상태 하나만 궁금할 때
- 이미 이번 세션에서 그 역할과 대화했을 때 — 스폰하면 맥락 없이 처음부터 다시 시작한다

## 파일 소유권

이 스킬 파일(`.claude/skills/**`)은 **리더 소유**다(헌법 제1조 4항에 따른 지정, 2026-07-29). 팀원은 읽기만 한다.

브리핑 중 팀원이 고칠 수 있는 것은 자기 `STATE.md`뿐이다. 헌법 제1조 1항의 소유권 표는 브리핑 중에도 그대로 적용된다.
