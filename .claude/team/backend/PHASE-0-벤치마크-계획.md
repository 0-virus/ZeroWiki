# Phase 0 벤치마크 실행 계획

**작성일:** 2026-07-31  
**최종 수정:** 2026-07-31 (리더 2가지 결정 반영)  
**상태:** 최종본  
**근거:** 기획서 23절, 25절; 요구사항 정의서 1.3~1.4절, 11절; ERD 8절 미확정 표

---

## 개요

Phase 0의 목표는 **36개 원본 기반 예비 벤치마크를 통해 Ingest 파이프라인·연결·모순 탐지의 기술적 타당성을 검증**하고, 5개 미확정 계약(UD-11·17·25·29)을 확정하는 것이다.

### 데이터셋 규모 주의

기획서 3절 MVP 가설과 AC-1·NFR-PRF-01·NFR-COST-03은 전부 "문서 100개" 기준이나, 실제 확보 가능한 NoteWiki는 원본 36개뿐이다(기획서 25절). **따라서 Phase 0는 36개로 예비 벤치마크를 실행하며, AC-1("문서 100개 완료율 95%")의 정식 검증은 Phase 1로 이관한다.** 토큰 비용, 처리 시간, UD-11·17·29 확정은 36개 규모에서도 기술적으로 충분하다.

**일정 추정:** 3~4주 (1인 개발 + 반복 측정 포함)  
**결과물:** `docs/Phase-0-벤치마크-결과.md` (NEW) + ERD·API 명세 업데이트

## 1단계: 데이터셋·평가 세트 준비 (선행 필수)

### 1-1. 기준 데이터셋 구성

**무엇:** 기획서 25절 1번에 명시된 "기존 NoteWiki 원본 36개·위키 페이지 152개"

**어떻게:**
- backend가 보유한 NoteWiki 데이터에서:
  - `sources` 테이블: 원본 36개 (범위: 논문·블로그·문서·동영상 자막 혼합, 언어는 영/한 혼합)
  - `pages` 테이블: 기존 종합 페이지 152개
  - 메타데이터 (원본 언어, 주제 분류, 소유자 라벨 포함)
- 모든 데이터는 **사용자 1인 계정 내부로 격리** (FR-SRC-04 준수)
- CSV 내보내기: `원본_36개.csv` (ID, 제목, 언어, 주제), `페이지_152개.csv` (ID, 제목, 타입, 버전)

**차단 요인 검토:**
- ✓ 기존 데이터가 있는가? → NoteWiki 사용 가정(별도 확인 필요)
- ✓ 데이터 정제가 필요한가? → 민감정보·비밀 검사(기획서 18절)

**소요 기간:** 2일 (데이터 정제 포함)

### 1-2. 평가 세트 구성 (기획서 25절 2번)

**무엇:** 기준 데이터셋에 대한 정답 레이블:
- **정답 연결:** 의미 있는 관계 (예: "개념 A가 개념 B를 설명한다")
- **모순 후보:** 의도적으로 삽입한 모순 (예: "주장 P와 주장 Q는 서로 다른 조건 하에서 나온 것인가?")

**어떻게** (확정):

**사용자가 직접 라벨링한다.** 공개 벤치마크 데이터셋(SQuAD, FEVER)은 36개 원본의 도메인·언어와 일치하지 않아 AC-3·AC-5 실측을 대체할 수 없다.

1. **연결 평가 세트 (20~30건 축소)**
   - 후보 선정: 152페이지 무작위가 아니라 이미 관련 있다고 알려진 주제 클러스터에서 시작
   - 태깅: UD-16 확정 7종 (`RELATED_TO`, `PART_OF`, `DEPENDS_ON`, `CAUSES`, `CONTRASTS_WITH`, `EXPLAINS`, `APPLIES_TO`) + 방향 + 확신도(high/medium/low)
   - **부정 예시 2~3건 포함 필수** (관련 없는 페이지 쌍 — 오탐 측정용)
   - 형식: `source_page_id, target_page_id, relation_type, direction, confidence, 근거_한줄`
   - 파일: `정답_연결_세트.csv`
   - 1건 소요 시간: 3~5분

2. **모순 평가 세트 (10~15건 축소)**
   - 후보: 시간 경과로 업데이트된 내용, 출처별로 다르게 서술된 내용 우선
   - 분류 5종 (API 명세 7.3절):
     - `TRUE_CONFLICT`: 명백한 사실 충돌 (예: "출판년도 불일치")
     - `TIME_CHANGE`: 시간에 따른 변화 (예: "기술 진화")
     - `CONDITION_DIFF`: 조건 차이 (예: "특정 환경에서만 성립")
     - `VIEWPOINT_DIFF`: 관점 차이 (예: "학파·전문가별 입장")
     - `POSSIBLE_CONFLICT`: 의심스러운 충돌 (명확하지 않음)
   - **부정 예시 2~3건 포함** (실제 모순 아님)
   - 형식: `claim_A_statement, claim_B_statement, classification, 판단_이유`
   - 파일: `정답_모순_세트.csv`
   - 1건 소요 시간: 5~10분

**선행 조건:**
- ✓ 사용자 직접 라벨링 확정
- CSV 템플릿과 라벨링 가이드 제공 필요 (아래 "라벨링 가이드" 섹션 참조)

**소요 기간:** 2~4시간 (5건 파일럿 + 본작업 20~30건+10~15건, 예상 총 35~45건)

## 2단계: 2단계 Ingest 프로토타입 실행 (핵심)

### 2-1. 프로토타입 구성

**무엇:** 2단계 AI 처리 파이프라인(Ingest 9단계 5~8 구현)의 프로토타입 실행

**대상 문서:** 1단계 데이터셋 36개 원본 → 약 100문단 또는 "의미 있는 절 단위" 분할 (UD-11에 따라 달라짐)

**처리 흐름:**
```
1단계 스캔(저비용)
  ├─ 파일 파싱 / 중복 탐색 / 민감정보 탐지 / 주제 분류
  └─ 기존 페이지(152개) 후보 자동 매칭 → 처리 계획 제시

처리 계획 승인 (사용자)

2단계 처리(고품질) — 핵심 측정 지점
  ├─ 핵심 주장·근거 추출 (Claim·Evidence)
  ├─ 기존 지식과 의미 연결 (Relation)
  ├─ 종합 페이지 작성 또는 기존 페이지 수정
  ├─ 모순 후보 판정 (Contradiction)
  ├─ 위험 변경 분류
  └─ 토큰 사용량·소요 시간 기록

초안 도서관에 변경 세트 적용 (검토 용이)
승인(일괄·개별) → 새 버전 발행
```

**실행 방식:**

```yaml
스크립트: backend/scripts/phase0-benchmark.sh (신규 작성)
  - Spring Boot CLI 또는 독립형 Jar로 Ingest 파이프라인 호출
  - 매개변수: --dataset="기준_데이터셋.csv" --benchmark-mode=true
  - 결과: 각 문서별 메트릭 CSV + 파이프라인 로그
```

**측정 항목 (NFR-PRF-05 기준):**

| 항목 | 단위 | 기록 방법 | 판정 기준 |
|------|------|---------|---------|
| **처리 성공률** | % | 성공 문서 / 전체 | **AC-1 예비:** 95% 이상? (정식 검증은 Phase 1로 이관) |
| **문서당 토큰 비용** | token/doc | 1단계 + 2단계 입출력 합계 (LLM API 로그) | NFR-COST-03: 평균값 기록, 분포 분석 |
| **1단계 스캔 시간** | sec/doc | Worker 로그 타임스탬프 | NFR-PRF-02: 처리 계획이 대기 가능한 시간? (기준: 2분 이내 권고) |
| **2단계 처리 시간** | sec/doc | Worker 로그 | NFR-PRF-05: 단계별·모델별 분포 측정 |
| **연결 정확도** | % | 출력 relations ∩ 정답_연결_세트 / 정답_연결_세트 | AC-3 기반: 70% 이상? |
| **모순 탐지율** | % | 탐지한 contradictions ∩ 정답_모순_세트 / 정답_모순_세트 | AC-5 기준: 80% 이상? |
| **모순 오탐율** | % | 탐지했으나 정답 아님 / 탐지한 총 개수 | 리스크 2번 평가 |

### 2-2. 실행 프로토콜

**단계별 수행:**

```
Week 1 (시작 D+1~D+7):
  Day 1-2: 스크립트 작성 (파이프라인 호출, 메트릭 수집)

  Day 15-16: UD-11(Claim 세밀도) 비교 실행 (모든 문장 vs 주요 주장 2회)

```

## 3단계: UD-29 + 갭 #23 (2단계와 병행)

### 3-1. UD-29: claim_key 생성 규칙 (의미 정규화 벤치마크)

**무엇:** 버전 간 Claim 재사용 구조에서 "같은 주장"을 판정하는 규칙 평가

**현재 상태:**
- ERD v1.5: claims.page_id FK 추가, claim_statuses 신설 (버전별 상태)
- 미확정: claim_key 동일성 판정 메커니즘 (UD-29)
- 권고: "의미 정규화는 불가능(해시의 한계) → AI 제안 + 사용자 승인 모델"

**벤치마크 계획:**
1. **수동 시나리오 (10~15개):** 같은 주장이 다양한 표현으로 나타나는 경우
   - 예: "Python은 해석형 언어다" vs "Python은 동적 타입의 스크립트 언어다"
   - 사람이 "같은가/다른가" 판정

2. **자동 제안 실행:** 2단계에서 생성된 Claims 쌍에 대해
   - Embedding 기반 유사도 측정
   - LLM 제안: "동일 Claim으로 취급? 이유?"
   - 정확도 측정 (recall·precision)

3. **결론:** 의미 정규화 불가능 → AI 제안 후 사용자 승인 필요 [재확인]

**소요 기간:** 2~3일 (2단계 결과 사용)

### 3-2. 갭 #23: REQUEST_CHANGES 재생성 평균 시간

**무엇:** 변경 검토 화면에서 "수정 요청 후 재생성" 시 항목 갱신 시간 측정

**메커니즘 (API 명세 8.1절 옵션 A 확정):**
```
POST /change-sets/{id}/items/{itemId}/request-changes
  → 202 Accepted

클라이언트 polling (2초 간격, UD-04 기본값)
GET /change-sets/{id}/items
  → change_items[].review_status: REVISION_REQUESTED → PENDING
  → change_items[].after_snapshot: 갱신된 결과

완료 감지: review_status 변화 감지
```

**측정 항목:**
- 재생성 요청 → 완료까지 소요 시간 (초)
- 규모별: 소/중/대 변경 항목 3개 측정
- polling 간격 2초가 적절한가? (99% 감지율 기준)

**실행:** 2단계 "위험 변경" 샘플에서 REQUEST_CHANGES 시뮬레이션

**소요 기간:** 1~2일 (2단계 완료 후)

## 라벨링 가이드 (사용자용)

Phase 0 벤치마크의 정답 세트를 사용자가 직접 작성합니다. 아래 가이드를 따르고 제공된 CSV 템플릿을 사용하세요.

### 준비 사항

- CSV 템플릿: `evaluation/relation-labels-template.csv`, `evaluation/contradiction-labels-template.csv`
- 예상 소요 시간: 전체 2~4시간 (5건 파일럿 + 35~45건 본작업)
- 편집기: Excel, Google Sheets, 또는 텍스트 에디터

### 1. 연결(Relation) 라벨링

**목표:** 의미 있는 페이지 간 관계 20~30건 표시

**단계:**

1. **파일럿 5건으로 형식 검증** (30분)
   - 템플릿 첫 5행 작성
   - CSV 형식 확인 (쉼표, 따옴표 인식)
   - backend에 피드백 (문제 있으면 즉시 수정)

2. **본작업 20~30건** (1.5~2.5시간)
   - 152페이지 중 관계가 있다고 알려진 클러스터부터 시작
   - 각 페이지마다 2~3개 정도의 관계 선택

**형식:**

```csv
source_page_id,target_page_id,relation_type,direction,confidence,label,근거_한줄
page-001,page-015,EXPLAINS,forward,high,positive,개념 A가 개념 B를 설명한다
page-045,page-067,RELATED_TO,bidirectional,medium,positive,두 기술이 보완 관계
page-102,page-103,PART_OF,forward,low,positive,더 큰 주제의 부분
page-050,page-051,,,low,negative,관련 없는 페이지 (오탐 측정용)
```

**필드 설명:**

- `source_page_id`: 출발 페이지 ID (예: `page-001`)
- `target_page_id`: 도착 페이지 ID
- `relation_type`: UD-16 확정 7종 중 하나 (**negative 행은 비워둔다**)
  - `RELATED_TO`: 주제가 연관됨
  - `PART_OF`: 목표가 더 큰 개념의 부분
  - `DEPENDS_ON`: 선행 학습 필요
  - `CAUSES`: 인과관계
  - `CONTRASTS_WITH`: 대비/반대 관점
  - `EXPLAINS`: 설명/근거 제공
  - `APPLIES_TO`: 실제 적용 예시
- `direction`: `forward`(일방향) / `bidirectional`(양방향) (**negative 행은 비워둔다**)
- `confidence`: `high` / `medium` / `low` (확신도)
- `label`: `positive`(의미 있는 관계) / `negative`(오탐 측정용, 관련 없음) — **positive와 negative 모두 포함 필수**
- `근거_한줄`: 왜 이 관계가 의미 있는가? (negative 행: 오탐 이유)

**부정 예시 2~3건 포함 (중요)**

negative 행은 `relation_type`과 `direction`을 **비워두고** `label`에 `negative`를 명시해야 한다. 이렇게 하면 파이프라인이 출력한 관계와 정답을 대조할 때, negative 행은 "모델이 어떤 관계로 잘못 예측해도 오탐으로 카운트할 수 있는" 기준이 된다. 즉, 모델이 page-050과 page-051 사이에 어떤 7종 관계로든 제안하면 오탐이다.

### 2. 모순(Contradiction) 라벨링

**목표:** 의미 있는 모순 10~15건 표시

**단계:**

1. **파일럿 5건** (30분)
   - 템플릿 첫 5행 작성
   - 분류 5종 확인 (각 유형 최소 1건씩)

2. **본작업 10~15건** (1~1.5시간)
   - 시간 경과로 업데이트된 내용 우선
   - 출처별로 다르게 서술된 내용 우선

**형식:**

```csv
claim_A_statement,claim_B_statement,classification,판단_이유
Python은 정적 타입 언어다,Python은 동적 타입 언어다,TRUE_CONFLICT,기본 특성에서 직접 충돌
메모리 구조 X는 Y바이트다,메모리 구조 X는 Z바이트다 (최신 표준),TIME_CHANGE,기술 버전 업데이트
이 알고리즘은 모든 환경에서 최적이다,이 알고리즘은 메모리 부족 환경에서는 비효율적이다,CONDITION_DIFF,조건에 따라 성능 달라짐
관점A: 이 정책은 효율적이다,관점B: 이 정책은 비효율적이다,VIEWPOINT_DIFF,전문가 입장 차이
이 현상은 원인 A 때문일 수 있다,이 현상은 원인 B 때문일 수 있다,POSSIBLE_CONFLICT,두 원인 모두 가능성 있음 (미확실)
```

**필드 설명:**

- `claim_A_statement`: 첫 번째 주장 (원문에서 인용, 100자 이내)
- `claim_B_statement`: 두 번째 주장
- `classification`: 5가지 중 하나
  - `TRUE_CONFLICT`: 명백한 사실 충돌 (예: 날짜, 통계, 기본 특성)
  - `TIME_CHANGE`: 시간 경과로 변화 (예: 기술 진화, 정책 변경)
  - `CONDITION_DIFF`: 조건에 따른 차이 (예: 환경, 상황, 대상)
  - `VIEWPOINT_DIFF`: 관점/입장 차이 (예: 학파, 전문가, 이념)
  - `POSSIBLE_CONFLICT`: 의심스러운 충돌 (명확하지 않음)
- `판단_이유`: 왜 이것이 모순인가? (한 줄)

**부정 예시 2~3건 포함 (중요)**

```csv
이것은 실제 모순이 아닙니다. 같은 주장을 다르게 표현했습니다.,이것도 같은 내용입니다.,NO_CONFLICT,같은 주장의 다른 표현 (오탐 측정용)
```
