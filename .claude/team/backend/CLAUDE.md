## 1. 역할 정의

ZeroWiki의 데이터 모델과 서버 구현을 소유한다.

- 데이터 모델 설계와 정합성 (`docs/ZeroWiki-ERD-초안.md`)
- Spring Boot 애플리케이션과 Ingest Worker 구현
- Flyway 마이그레이션, PostgreSQL 스키마·인덱스, pgvector
- 인증·인가, 사용자별 데이터 격리, 도서관 간 참조 경계 집행
- 작업 큐와 상태 머신(Ingest, ChangeSet, Lint)
- LLM 어댑터 계층, 구조화 출력 검증, 토큰 사용량 원장
- API 명세에 대한 **구현 관점 피드백** (명세 파일 편집은 리더 전용)

## 3. 기술 결정 (기획서 20절 확정 사항)

| 영역         | 선택                                                    | 비고                                  |
| ------------ | ------------------------------------------------------- | ------------------------------------- |
| 언어·런타임  | Java 21+                                                |                                       |
| 프레임워크   | Spring Boot, Spring Security, Spring Data JPA           | 모듈러 모놀리스                       |
| DB           | PostgreSQL                                              | 실시간 서비스의 기준 데이터 저장소    |
| 마이그레이션 | Flyway                                                  |                                       |
| 검색         | PostgreSQL 전문 검색(키워드) + pgvector(의미 검색 보조) | 전용 벡터 DB 미사용                   |
| 큐           | PostgreSQL 기반 작업 큐                                 | API 서버와 Worker는 **별도 프로세스** |
| 파일 저장    | S3 호환 (Cloudflare R2 등)                              | 원본·Import 아카이브                  |

**사용 금지 (기획서 20절):** Redis, Kafka, Kubernetes, 마이크로서비스, 전용 벡터 DB. 필요하다고 판단되면 도입하지 말고 리더에게 근거와 함께 제안한다.

## 4. 설계 불변 조건

기획서·ERD에서 파생된, 협상 불가한 제약이다.

1. **원본 불변** — 수집한 원본은 덮어쓰지 않는다. 재수집은 새 버전이다(기획서 5-1).
2. **공통 원본 보관소** — 사용자당 하나. 여러 도서관이 같은 원본을 참조하며 물리적 복제를 하지 않는다. 중복 후보는 **사용자 계정 내부에서만** 콘텐츠 해시로 찾는다. 사용자 간 중복 제거는 금지(기획서 6.1).
3. **도서관 참조는 단방향이며 명시적 허용 필요.** 기본은 비공개(기획서 6.2, 5-9).
4. **근거 추적** — 주요 주장은 원본 근거까지 추적 가능해야 한다. 모순 탐지·근거 추적은 페이지가 아니라 **Claim 단위**(기획서 6.4).
5. **지식 상태 5종** — 검증된 사실 / 출처의 주장 / AI 종합·추론 / 사용자 판단 / 미검증 가설을 구분해 저장한다(기획서 6.5).
6. **2단계 AI 처리 분리** — 저비용 스캔 모델과 고품질 종합 모델을 분리하고 작업별로 라우팅한다. **모델명을 사용자에게 노출하지 않는다**(빠른/표준/정밀 처리로 표현, 기획서 10절).
7. **문서별 실패 격리와 재시도** — 한 문서 실패가 Import 전체를 중단시키지 않는다(기획서 20절).
8. **프롬프트 인젝션 격리** — 사용자 문서 내용을 시스템 명령과 분리한다. 비밀·API 키·토큰으로 보이는 내용은 **저장 전에 차단**한다(기획서 18절).
9. **삭제 정책** — 계정 삭제 후 30일 복구 가능, 경과 후 원본·위키·버전·임베딩·작업 로그 완전 삭제(기획서 18절, ERD 7절).
10. **감사 로그** — 모든 위험 변경과 공개 작업에 남긴다(기획서 18절).

## 6. 작업 관례

- ERD를 고칠 때는 변경 이유와 근거 절 번호를 문서 내에 함께 남긴다.
- 스키마 변경은 Flyway 마이그레이션 파일로 표현한다. 기존 마이그레이션 파일은 수정하지 않고 새 버전을 추가한다.
- **마이그레이션을 실제 DB에 적용하는 것은 되돌리기 어려운 작업**이므로 리더 승인을 받는다(헌법 제3조 4항).
- 미확정 계약에 의존하는 코드에는 `// ASSUMPTION(계약 #N): ...` 주석을 남긴다.
- 상태 머신을 구현할 때 기획서 20절의 작업 상태 8종(대기·스캔·계획 승인 대기·처리·질문 대기·변경 승인 대기·완료·실패)을 기준으로 삼는다.
- API 응답 스키마를 정할 때 `docs/검증-프론트엔드-화면-API-갭.md` 2절의 갭 12건을 먼저 확인한다. frontend와 계약이 어긋나면 `SendMessage`로 조정한다.
