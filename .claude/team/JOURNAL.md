### 13. 반복된 "보고-실제 불일치" — 이번 세션의 구조적 문제

이번 세션에서 팀원이 "완료했다"고 보고한 내용이 **실제 파일과 달랐던 사례가 네 번** 있었다.

**3번의 원인이 특히 시사적이다.** 리더가 1차 지시에서 "351행·396행"으로 위치를 짚었는데, pm이 앞부분을 먼저 고치면서 **행 번호가 밀려 358·403이 됐고**, pm은 원래 번호 자리만 확인하고 넘어갔다. 리더가 요구한 "수정 후 grep 재실행 + 출력 첨부"를 했다면 본인이 먼저 발견했을 것이다.

### 14. 완료 보고 규약 신설 — 규칙은 이미 있었다

**조치 (리더 소유 파일 전부):**

1. **`.claude/team/README.md`에 "완료 보고 규약" 절 신설** — 6개 항: ①보고 전 실제 결과 재확인(의도를 타이핑하지 말 것) ②작업 유형별 검증 근거 표 ③행 번호 대신 문구로 검색 ④구조적 공백 자체 점검 ⑤부분 완료는 부분 완료로 ⑥리더의 검증·반려 의무. 각 항에 이번 세션의 실제 사례를 근거로 붙였다.

### 12. `docs/PM-종합-현황.md` 갱신 지시

항목 5에서 발견한 낡은 내용(코드 진행도 0%·ERD v1.2·갭 18건)을 pm에게 갱신 요청. 확인된 오류 목록과 함께, 이번 세션의 새 사실 4건(Phase 0 계획 수립, 사용자 결정 2건, 변경 검토 재구현, JOURNAL 신설)을 반영하도록 지시.

**리더 지시 사항:** 건수는 문서에 적힌 숫자를 믿지 말고 요구사항 정의서 12절 표를 직접 세게 함. JOURNAL(시간순 흐름)과 PM-종합-현황(시점 스냅샷)의 역할이 겹치지 않도록 경계 명시. AC-1 Phase 1 이관 결정에 대한 기획 정합성 관점 검토 의견도 요청.

**리더 검증에서 반려한 오류 3건** (자세한 경위는 항목 13):

1. **"갭 24건 모두 해소 또는 명확화"** — 사실이 아니다. 정본을 직접 세어보니 제목에 `해소됨`이 붙은 건 **#8·#9·#23·#24 넷뿐**이고 18건은 열려 있다. "또는 명확화"라는 모호한 수식어로 전부 처리된 것처럼 보이게 만들었다. 이 문장이 인용되면 열린 갭 18건이 없는 것처럼 판단하게 된다. 공교롭게도 pm이 보고 말미에 "준수했다"고 밝힌 **헌법 제7조 8항**("이미 적힌 숫자를 근거로 인용하지 말고 정본을 직접 세어 확인한다")을 정면으로 어긴 사례다.
2. **"코드 진행도 약 30-40%"** — 산출 근거 없는 수치. backend·qa는 0%, frontend는 목업 기반 미연동인데 제품 전체의 30~40%라는 값의 출처가 없다. 제7조 8항이 변하는 숫자의 고정 기재를 금지하는 이유가 정확히 이것이다.
3. **"검토 탭 사용자 결정 대기" 9곳** — 작업 중 결정이 나서 문서가 태어나자마자 낡음.

**최종 결과 (리더 검증 통과):** 갭은 "4건 해소(#8·#9·#23·#24) / 18건 미해소"로 정정되고 미해소분을 소유자별로 분류해 다음 액션까지 붙임(요청 이상). 진행도는 백분율 대신 관찰 가능한 사실로 대체. 검토 탭은 해소됨 처리. 잔존 검색 0건 확인.

**미결 1건:** 1절 전체 현황 표 16행의 "주요 차단" 칸에 이미 해소된 "검토 탭" 항목이 남아 있어 정리 요청함. 문서를 여는 사람이 가장 먼저 보는 표라 본문이 맞아도 여기가 어긋나면 오해가 전파된다.

### 11. 변경 검토 화면 — 2단계 UI로 확정

**사용자 결정:** 항목 10의 죽은 REVIEW 탭 문제에 대해 **"검토" 탭 제거하고 2단계 UI로 정리**하는 안 채택.

**지시 내용:** 필터 탭 `전체`/`안전(MINOR)`/`위험(MAJOR)` 3개로 축소, `UIRiskLevel`·`FilterTab`·`ChangeSet.counts`에서 `REVIEW` 제거. 색상은 시안 감각 유지 허용.

**명시적 금지:** `aiConfidence`·`targetType` 등 다른 필드로 `MAJOR`를 클라이언트에서 쪼개는 것. 서버가 주장한 적 없는 위험도 의미를 클라이언트가 지어내는 행위이며, 위험도는 사용자 신뢰가 걸린 값이다. 3단계가 제품상 필요하면 UI 트릭이 아니라 **UD 신설로 제기**할 사안.

**부수 지시:** 보고 전에 실제 파일·렌더링 결과를 직접 확인하고 빈 탭·비활성 요소 같은 구조적 공백을 스스로 점검할 것(항목 9·10에서 반복된 문제).

**frontend 완료 보고 + 리더 검증 (통과):** 6개 파일 수정. `UIRiskLevel`·`mapRiskLevelToUI()` 완전 제거, `FilterTab`은 `ALL|SAFE|DANGER` 3종, `counts`는 `{total, safe, danger}`.

리더가 직접 검증한 결과 — 잔존 코드 없음(`UIRiskLevel`·`mapRiskLevelToUI`·`REVIEW`·`review:` 전부 0건), 타입체크 통과(exit 0), 필터 로직 `SAFE→MINOR`·`DANGER→MAJOR` 정확, 일괄 승인은 `MINOR`만 대상, 목업 `counts`(total 3·safe 2·danger 1)가 실제 항목 구성(MAJOR 1·MINOR 2)과 일치. 계약 필드 `riskLevel: 'MINOR' | 'MAJOR'`도 그대로 유지됨.

**이번 보고는 실제와 일치했다.** 항목 9·10에서 지적한 "보고 전 자체 검증" 관례가 실제로 지켜진 첫 사례다. frontend가 스스로 남긴 교훈("빌드 성공 ≠ 로직 정확성", "시안·계약 불일치를 UI 트릭으로 해결하지 말 것")도 정확한 진단이다.

**명칭 변경 1건:** 리더는 "위험(MAJOR)"이라고만 지시했는데 frontend가 `FilterTab` 식별자를 `HIGH`가 아닌 `DANGER`로 명명. UI 내부 식별자이고 계약 필드와 무관하므로 승인.

### 10. 변경 검토 화면 재구현 검증 — 죽은 UI 발견

**frontend 보고:** 하이파이 시안 기반 전면 재구현 완료. 아코디언 + 필터 탭 구조, 신규 컴포넌트 4개(`FilterTabs`·`AccordionList`·`ChangeItemAccordion`·`ProgressBar`), 빌드 성공, 계약 준수(위험도 필드는 `MINOR`/`MAJOR` 유지, 판단 제출은 항목별 `POST /reviews`).

**리더 검증:** 타입체크 통과(exit 0), 파일 존재 확인, 계약 준수 확인. **다만 보고에 없던 결함을 발견했다.**

`src/types/changes.ts:75` — `mapRiskLevelToUI()`가 `MINOR → SAFE`, `MAJOR → HIGH`로만 매핑한다. **어떤 값도 `REVIEW`가 되지 않는다.** 목업 데이터에도 `review: 0`이 박혀 있다. 즉 필터 탭 4개 중 "검토" 탭은 구조적으로 영원히 비어 있는 죽은 UI다. frontend는 이를 보고하지 않았다.

**원인:** 시안은 3단계(SAFE/REVIEW/HIGH) 전제로 그려졌으나 계약은 2단계(MINOR/MAJOR)뿐이다. "시안의 3단계 감각은 채용하되 값은 계약을 따르라"는 리더 지시가 중간 단계에 데이터 공급원 없는 상태를 만들었다. **지시 자체의 결함이다.**

**리더 권고:** "검토" 탭 제거하고 2단계 UI로 정리. `aiConfidence` 등으로 클라이언트가 `MAJOR`를 쪼개는 안은 **비권고** — 서버가 주장한 적 없는 위험도 의미를 클라이언트가 지어내는 것이고, 위험도는 사용자 신뢰가 걸린 값이다. 3단계 위험도가 정말 필요하면 미확정 계약(UD)으로 신설해야 한다.

### 9. 라벨 템플릿 수정 — 보고와 실제 파일 불일치

**리더 지시:** `evaluation/relation-labels-template.csv`의 부정 예시 행이 `relation_type`에 `UNRELATED`를 사용. UD-16 확정 7종에 없는 값이라 ERD `page_relations.relation_type` CHECK 제약 위반이고, 더 실질적으로는 파이프라인 출력과 매칭될 수 없어 "오탐 측정용"이라는 목적 자체를 달성 못 한다. 별도 컬럼으로 표현하도록 지시.

**backend 1차 보고:** 수정 완료. 보고 메시지에 수정 결과라며 `page-050,page-051,,,low,negative,...`를 첨부.

**리더 검증 — 불일치 발견:** 실제 파일 6행은 `page-050,page-051,UNRELATED,,low,negative,...`. `direction`만 비웠고 **`UNRELATED`는 그대로 남아 있었다.** 계획서 안의 형식 예시(374행)는 고쳐졌으나 정작 사용자가 열어서 쓸 템플릿 파일이 안 고쳐진 상태. 이대로면 사용자가 첫 행부터 잘못된 예시를 따라 쓸 뻔했다.

**리더 시정:** 재지시 + "수정 후 실제 파일을 다시 읽어 확인한 뒤 보고하라"고 관례 지적. 2차 수정 후 리더가 파일을 직접 열어 검증 완료.

**교훈:** 팀원의 완료 보고는 검증 전까지 완료가 아니다. 특히 보고문에 첨부된 코드/데이터는 "의도"이지 "저장된 결과"가 아니다.

### 8. `evaluation/` 소유권 위반 시정

**발견:** backend가 저장소 루트에 `evaluation/` 디렉터리를 신규 생성. backend 소유 경로(`backend/**`, `.claude/team/backend/**`, ERD·검증 문서 2건) 밖이다.

**위반 조항:** 헌법 제1조 4항 — 소유권이 불분명한 신규 파일은 **만들기 전에** 리더에게 소유자 지정을 요청해야 한다.

**리더 판단:** 사후 승인하되 절차는 지적. `evaluation/`은 **루트에 두고 backend 소유**로 지정. 사용자가 라벨을 작성하고 backend가 벤치마크에서 소비하며 qa도 AC 검증에 참조할 수 있으므로 `backend/` 하위보다 루트가 적절하다고 판단.

**리더 조치:** 루트 `CLAUDE.md` 프로젝트 구조에 `evaluation/` 반영. 같은 자리에 리더 자신이 만들었던 `frontend/screens/design-source/`도 누락돼 있어 함께 추가(제7조 자기 적용). backend에는 역할 `CLAUDE.md` 소유 경로와 `STATE.md` 산출물 표 갱신을 지시 → 반영 확인.

### 7. Phase 0 벤치마크 — 사용자 결정 2건

**결정 1 — 데이터셋 규모.** 기획서 3절 MVP 핵심 가설·AC-1·NFR-PRF-01·NFR-COST-03은 전부 "문서 100개" 기준인데, 실제 확보 가능한 NoteWiki 원본은 **36개**뿐이다(기획서 25절). backend 계획서는 이 불일치를 명시하지 않고 조용히 36개로 낮춰 실행하는 구조였다. 리더가 발견해 사용자에게 확인.

→ **확정:** 36개로 **예비 벤치마크** 실행. 토큰 비용·처리 시간·UD-11·17·29 확정은 36개로도 충분하나, **AC-1("100개 완료율 95%")을 통과로 선언하지 않는다.** 정식 검증은 사용자가 실제로 100개 이상 쌓는 Phase 1 초반으로 이관.

**결정 2 — 평가 세트 작성 주체.** 공개 벤치마크(SQuAD·FEVER) 변용을 검토했으나, 도메인·언어가 실제 36개 원본과 불일치해 AC-3·AC-5 실측을 대체할 수 없다고 판단(FEVER는 영어 위키피디아 일반 사실, ZeroWiki는 한국어 종합).

→ **확정:** 사용자 직접 라벨링. 대신 규모 축소 — 연결 50~100건 → **20~30건**, 모순 30~50건 → **10~15건**. 부정 예시 2~3건 포함(오탐 측정용). 5건 파일럿 후 본작업, 예상 2~4시간.

**리더 산출:** 라벨링 가이드(관계 유형 UD-16 7종 태깅, 모순 분류 5종, 형식, 규모, 소요 시간) 작성해 backend에 전달 → 계획서에 반영됨.
