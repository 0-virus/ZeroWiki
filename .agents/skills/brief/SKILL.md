# ZeroWiki brief

이 절차는 주 에이전트가 직접 수행한다. 하위 에이전트를 생성하거나 어떤 파일도 수정하지 않는다.

## 입력

인자가 없으면 `backend`, `frontend`, `qa`, `pm` 전부를 본다. 역할 인자가 있으면 지정된 역할만 본다. 허용 역할 밖의 값은 오타 가능성을 사용자에게 확인한다.

## 절차

1. `git log --oneline -10`과 `git status --short`로 저장소 현실을 먼저 확인한다. dubious ownership 오류가 나면 현재 명령에만 `-c safe.directory=<repo-root>`를 사용하고 전역 Git 설정은 바꾸지 않는다.
2. 대상 역할의 `.claude/team/{역할}/STATE.md`, `WORKLOG.md`, `CLAUDE.md`를 읽는다. 서로 독립적인 파일 읽기는 병렬화한다.
3. 전원 브리핑이면 `.claude/CONSTITUTION.md`, `.claude/team/JOURNAL.md`, `docs/ZeroWiki-요구사항-정의서.md` 12절도 읽는다.
4. 각 역할에 대해 다음을 판정한다.
   - 지금 바로 시작할 수 있는 일
   - 막힌 일과 해소 주체: 사용자 결정 / 다른 역할 / 벤치마크 / 리더 확정
   - STATE와 실제 저장소의 차이
   - 다른 역할에서 받아야 할 것
   - 우선순위 1순위와 근거
5. 역할 간 의존 사슬과 모순을 찾고, 사용자만 풀 수 있는 결정을 한 묶음으로 정리한다. 기술 결정은 사용자 결정으로 잘못 올리지 않는다.
6. 선택지를 늘어놓지 말고 다음 한 걸음 하나를 권고한다.

## 검증

- STATE의 “완료”를 그대로 믿지 말고 실제 산출물을 연다.
- 수치·분량은 명령으로 직접 세고, 분모 없는 백분율은 사용하지 않는다.
- UD 번호와 결정 주체는 요구사항 정의서 12절에서 확인한다.
- 요구사항 ID, 일정, 계약 값이 실제 정본에 존재하는지 검색한다.
- STATE가 최근 관련 커밋보다 오래됐으면 놓친 커밋과 영향을 명시한다.
- “모두 이상 없음”이라고만 쓰지 말고 무엇을 어떻게 대조했는지 근거를 제시한다.

판단에 깊은 코드 조사나 역할별 기술 결정이 필요하면 브리핑 범위를 넘었다고 알리고 별도 팀 작업을 제안한다. 브리핑 안에서 몰래 실행하지 않는다.
